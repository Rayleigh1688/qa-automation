# 测试自动化总体规划

## 项目目标

建设一套可持续演进的测试自动化体系，用自动化覆盖核心业务链路、重要业务规则、完整回归、CI 门禁、性能验证和问题定位能力。

本项目优先解决以下问题：

- 核心链路每次发版前都能快速、稳定地回归。
- API 与 UI 自动化分层建设，减少只依赖 UI 用例导致的维护成本。
- 测试失败能被快速定位，失败原因、已知问题和排查经验能持续沉淀。
- 自动化结果能进入 CI 流水线，逐步形成可执行的质量门禁。
- 后续 AI 辅助、性能测试、可观测性能力建立在稳定的基础测试资产之上。

## 阶段划分

- Phase 1：P0 核心自动化
- Phase 2：P1 重要业务自动化
- Phase 3：P2 完整回归
- Phase 4：CI 质量门禁
- Phase 5：AI 测试增强
- Phase 6：性能测试
- Phase 7：可观测性与性能定位

## 优先级定义

### P0

P0 是必须优先自动化的核心链路。满足任一条件即可归入 P0：

- 阻塞登录、注册、充值、下单、支付、结算、提现等主流程。
- 失败后会直接影响线上核心收入、核心用户路径或关键运营动作。
- 每次发布都必须手工回归，且手工回归成本高、遗漏风险高。
- 具备稳定测试环境、稳定账号和可验证的 API 或 UI 入口。

### P1

P1 是重要业务自动化。满足任一条件即可归入 P1：

- 影响重要业务模块，但不一定阻塞核心链路。
- 涉及复杂业务规则、状态流转、权限、配置或边界条件。
- 线上问题出现频率较高，适合通过自动化降低回归遗漏。
- 可在 P0 框架稳定后复用基础能力快速扩展。

### P2

P2 是完整回归和长尾场景。满足任一条件即可归入 P2：

- 覆盖低频业务、异常路径、兼容性、历史问题回归和非核心配置组合。
- 单个场景风险不高，但整体覆盖面影响版本信心。
- 执行耗时较长，不适合阻塞所有提交，但适合夜间、发版前或按需执行。
- 需要依赖更多测试数据准备、环境状态或跨系统联动。

## 总体完成标准

- P0 核心链路自动化稳定运行，并形成明确的用例清单、执行方式和失败处理流程。
- P1/P2 用例有可维护的分层策略，API 优先、UI 补充，避免重复覆盖。
- Jenkins 或等效 CI 能按分支、定时或人工触发执行自动化任务。
- 自动化报告包含通过率、失败用例、失败截图或日志、执行耗时和历史趋势。
- `skills/` 中沉淀测试方法、业务规则和用例设计约定。
- `harness/` 中沉淀调试记录、已知问题、 flaky 用例和失败分析。
- 敏感信息通过本地配置或 CI 凭据管理，不提交到 Git。

## 暂不处理

以下内容暂不作为第一轮建设目标：

- 一次性追求全量自动化覆盖。
- 在 P0 稳定前引入复杂平台化能力。
- 对生产环境执行有副作用的自动化操作。
- 把 AI 生成结果直接作为可执行用例，不经过人工评审。
- 把性能测试结果作为硬门禁，除非已有稳定基线和环境隔离。
