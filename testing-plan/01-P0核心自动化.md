# P0 核心自动化

## 阶段目标

完成核心业务链路的第一批自动化，让每次发布前都能用较短时间验证系统是否具备基本上线条件。

P0 阶段重点不是追求覆盖率，而是先建立稳定、可信、可重复执行的自动化基座。

## 前置条件

- 已明确 P0 核心链路清单，并标注业务负责人、测试负责人和验收方式。
- 有可重复使用的测试环境、测试账号、测试数据和必要的权限。
- API 文档、关键页面入口、业务规则和断言口径基本明确。
- 能隔离或清理测试数据，避免自动化执行污染环境。
- 敏感配置通过本地环境变量或 CI 凭据注入。

## 本阶段范围

### API

- 登录、鉴权、会话刷新和权限校验。
- 核心实体的创建、查询、更新、状态流转和取消。
- 核心交易链路的正向路径、关键失败路径和幂等校验。
- 关键字段断言，包括状态码、业务码、金额、数量、状态、时间和关联 ID。
- 测试数据准备与清理接口，优先封装为可复用 helper。

### UI

- 覆盖 API 无法完全证明的关键用户路径。
- 覆盖核心页面能否加载、关键按钮能否点击、关键结果能否展示。
- UI 用例只保留高价值端到端路径，避免把所有业务规则都压到 UI 层。
- 保存失败截图、页面 HTML、网络错误和必要的控制台日志。

### 框架

- 建立统一目录结构：`api/`、`ui/`、`scripts/`、`performance/` 按职责拆分。
- 建立环境配置、账号管理、请求封装、断言封装和日志规范。
- 采用“独立接口操作 + 场景组合”模型：每个 runner/线程组启动时 fresh login，token 只保存在本次运行上下文；KYC、充值、投注、提现等操作可独立执行，也可由编排器按 P0 顺序组合，不跨运行复用认证状态。
- 建立用例命名、标签、优先级、重试和失败归档约定。
- 约定本地执行命令和 CI 执行命令。
- 明确 flaky 用例处理流程：发现、标记、归因、修复、恢复。

## 实施步骤

1. 梳理 P0 链路清单，按业务风险和执行频率排序。
2. 为每条链路补齐输入数据、前置状态、操作步骤、断言点和清理方式。
3. 优先实现 API 自动化，覆盖核心业务规则和状态流转。
4. 为必须从用户视角验证的链路补充少量 UI 自动化。
5. 接入统一报告、日志、截图和失败归档。
6. 连续运行多轮，修复环境问题、数据问题和 flaky 问题。
7. 输出 P0 阶段验收报告和后续扩展建议。

## 产物

- P0 用例清单。
- API 自动化用例与公共 helper。
- UI 自动化冒烟用例。
- 本地执行说明。
- 测试配置示例，不包含真实密钥。
- 自动化执行报告，作为最近一次生成物保存，不作为长期固定资产。
- flaky 和已知问题记录。

## 验证方式

- 本地完整执行 P0 自动化至少 3 次，确认结果稳定。
- 在同一测试环境中重复执行，确认测试数据可复用或可清理。
- 手工抽查自动化断言是否覆盖真实业务验收点。
- 故意制造一个可控失败，确认报告、日志和截图能支持定位。

## 完成标准

- P0 用例通过率达到 95% 以上，且失败项均有明确原因。
- 连续 3 次执行没有环境外的随机失败。
- 所有 P0 用例都有负责人、优先级、断言说明和执行入口。
- 测试账号、Token、Cookie、密钥不出现在仓库文件中。
- 新成员可按 README 或阶段文档在本地跑通 P0 用例。

## 暂不处理

- P1/P2 长尾场景。
- 大规模并发、压力和容量测试。
- 复杂 AI 用例生成和智能失败分析。
- 跨浏览器全量兼容性矩阵。
- 生产环境写操作自动化。
