# 可观测性与性能定位

## 阶段目标

补齐自动化失败和性能问题定位所需的观测能力，让测试报告、日志、指标和链路追踪能相互关联，减少排查时间。

## 前置条件

- 自动化测试已能输出用例 ID、请求 ID、环境、账号和执行时间。
- 被测系统具备基本日志、指标或链路追踪能力。
- 已明确可收集的信息范围，避免泄露敏感数据。
- 性能测试或 CI 执行中能访问必要的观测平台或导出数据。

## 本阶段范围

### Metrics

- 服务 CPU、内存、磁盘、网络等基础资源指标。
- 接口响应时间、吞吐、错误率、超时率。
- 数据库、缓存、队列和第三方依赖指标。
- 自动化执行维度的通过率、失败率、耗时和 flaky 趋势。

### Logs

- 自动化执行日志。
- API 请求响应摘要，避免记录敏感字段。
- 服务端错误日志和关键业务日志。
- UI 控制台日志、网络错误和截图。
- 已知错误和排查结论沉淀到 `harness/known-errors.md`。

### Trace

- 核心链路请求 ID 或 trace ID 透传。
- 跨服务调用耗时和错误节点定位。
- 性能测试中慢请求的链路追踪。
- 自动化报告中关联 trace 或日志查询入口。

## 实施步骤

1. 统一自动化执行中的用例 ID、请求 ID 和 trace ID 记录方式。
2. 梳理 P0/P1 核心链路需要查看的指标、日志和 trace。
3. 在测试报告中增加日志、截图、请求摘要和 trace 关联信息。
4. 建立常见失败分类和排查路径。
5. 将重复问题沉淀到 `harness/` 文档。
6. 和性能测试结果对齐，形成瓶颈定位流程。

## 产物

- 观测字段规范。
- 自动化报告关联信息规范。
- 常见失败排查流程。
- 性能问题定位流程。
- 已知错误和 flaky 用例沉淀文档。

## 验证方式

- 使用一次真实或模拟失败，验证能从测试报告定位到日志和 trace。
- 使用一次慢请求，验证能关联到指标变化和调用链。
- 抽查报告中是否包含足够上下文且不暴露敏感信息。
- 复盘排查耗时是否比纯手工查日志更短。

## 完成标准

- P0/P1 失败报告能提供定位所需的核心上下文。
- 常见失败能按分类进入固定排查路径。
- 性能问题能关联指标、日志和 trace。
- 敏感字段有脱敏或不采集策略。

## 暂不处理

- 建设完整 APM 平台。
- 对所有系统做全量 trace 改造。
- 在没有数据治理前采集完整请求响应正文。
- 将观测平台告警作为第一阶段硬门禁。
