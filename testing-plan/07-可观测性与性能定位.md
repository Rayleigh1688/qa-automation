在这个四节点分散模型里，9个至少有一台承载3个，退出后剩6个，所以10是满足“退出任一节点后仍至少7个承载位”的最少数学数量；**未建议直接上10个**。10个相对原2个，保持0.256核request增加2.048核／2 GiB内存request，全部改0.7核则CPU request增加6.488核。也可另验8个掉一节点后、余6个平均约0.7656核的较高运行预算，但低于所见limit并不等于延迟与恢复达标。节点退出还会损失其他服务，不能只凭admin数量证明整个系统容灾。

副本方案也改变连接预算：若每Pod池上限为p且保持不变，所见2Pod的2p到8Pod为8p、到10Pod为10p，上限分别4倍／5倍；这不是实际连接数一定增加同样倍数。未取得p、DB容量和池等待时，不能只凭主机CPU低扩大副本／连接池。只有现有节点满足调度、资源争用和选定故障目标，固定规格节点内扩副本的新增服务器费才可能为0。

### 负载差异的解释与其他优化候选（2026-10-19）

真实负载差异即使存在，也要区分请求数、单次请求成本、并发／等待和机器能力，目标是改善尾延迟、成功率及资源效率，不要求所有Pod的CPU曲线完全相同。以下是一般机制，**不是本生产环境已确认根因**：

| 可能机制 | 为什么会表现不均 | 可区分它的证据 |
| --- | --- | --- |
| 长连接、会话保持、部分后端未接流量 | 链路若按连接选后端，少数长连接可把请求固定到部分Pod；会话保持、ready状态及本地路由也可能缩小后端集合 | 同窗各Pod请求数／活跃连接、实际ready集合、发布时间和路由设置；不能仅凭CPU判断 |
| 每次请求工作量不同 | 同为100个请求，缓存命中、拒绝返回、读库、复杂计算的成本不同；后台任务也可能只在部分实例运行 | 同窗路由／业务结果构成、耗时、CPU与请求量关系；请求数接近而CPU差很多时，不应先改分流算法 |
| Pod或宿主机差异 | 冷启动／缓存预热、GC、版本差异和邻居争抢资源，会让相同流量产生不同资源与延迟表现 | Pod启动／重启时间、节点CPU／内存／IO、节流与延迟是否同时变化；只有CPU低不代表没有等待 |

机制依据：[Kubernetes连接选择、会话保持与流量策略](https://kubernetes.io/docs/reference/networking/virtual-ips/)、[Google SRE负载分配与请求成本差异](https://sre.google/sre-book/load-balancing-datacenter/)。当前没有额外查询入口时，先用已有Pod／节点曲线和可读日志交叉验证；缺少每Pod请求数就保留归因未知，不重复把指标流数或日志行数当请求数。

### 容量检查首先看哪些约束

1. **主链路与依赖上限**：每Pod请求／并发、CPU限流与内存、DB连接／锁等待／慢查询／IO、Redis延迟／内存／热点、队列生产消费速率及消息年龄、厂商账户级限额、负载均衡连接和网络容量。特别核算“最大Pod数×每Pod连接池”和每请求对下游的调用／重试放大，不能只扩应用副本。
2. **扩容是否能及时生效**：HPA实际指标来源、当前状态和最大副本数，节点调度／配额、镜像拉取、启动／就绪、缓存预热及缩容稳定性。Prometheus的kubelet采集失败不直接证明HPA失效；HPA可能使用metrics-server或自定义指标，需单独核实。[Kubernetes HPA说明](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)、[节点扩容限制](https://kubernetes.io/docs/concepts/cluster-administration/node-autoscaling/)。
3. **过载时保住正确性**：业务约定哪些展示／报表请求可以降级，哪些资金／注单事件必须持久化和保持幂等；明确超时后的未知结果如何查证，避免重试、补偿或回调重放导致重复记账。不能用返回HTTP 200或丢弃财务事件来维持表面成功率。
4. **后台与观测的资源竞争**：优先核RisingWave、Vector、OB摄取／索引／缓冲的增长趋势、积压及失败策略。只要出现与主链路争抢资源、日志阻塞业务或关键审计丢失，就与容量约束一起处理；否则降噪和成本治理并行推进。

集群CPU约20.6%、内存31.9%是前轮快照，不能按比例推算“还能承载几倍”。容量上限须由代表性工作负载、依赖约束和验证结果共同确定；隔离环境达标也需要核对生产差异。[Google SRE容量规划与过载原则](https://sre.google/sre-book/service-best-practices/)。

可复核SQL如下，时间必须在UI中固定为上述168小时。`LIMIT 20`只限制返回的分钟桶，**不会把7天聚合扫描压缩为20条原始记录**；语法依据[官方histogram说明](https://openobserve.ai/docs/reference/sql-functions/aggregate/)。

```sql
SELECT histogram(_timestamp, '1 minute') AS minute_bucket,
       COUNT(*) AS request_count
FROM "nginx"
WHERE requested_server_name != '-' AND requested_server_name IS NOT NULL
GROUP BY minute_bucket
ORDER BY request_count DESC, minute_bucket ASC
LIMIT 20;
```

成本与只读边界：先试1小时，757 ms／448 MB；7天聚合21,973 ms／91.95 GB；最高分钟域名／状态复核51 ms／1,014 MB，接口Top10为122 ms／1,014 MB，10分钟趋势156 ms／1.38 GB。这是5次手动SQL查询的页面报告，另有1次手动图表运行；扫描量不当作实际磁盘IO。Dashboard自动加载若干面板，Go To Logs另自动执行原PV查询（184 ms／181 MB）；图表切换还会触发预览请求，不能声称本轮后台总共只有6次请求。仅一次7天范围聚合；未导出历史日志、保存查询／面板、改采集或远端配置。

补查也发现PolarDB CPU面板的Query Inspector实际使用`AliyunPolardb_cluster_cpu_utilization{clusterId=~"$clusterId",nodeId=~"$nodeId"}`，两个变量在所见Query中仍未替换且面板No Data。它是需继续核查的现成入口，不能再仅凭mysql／rds关键词未命中就推断数据库没有指标。

## 阶段目标

补齐自动化失败和性能问题定位所需的观测能力，让测试报告、日志、指标和链路追踪能相互关联，减少排查时间。

## 前置条件

- 自动化测试已能输出用例 ID、请求 ID、环境、账号和执行时间。
- 被测系统具备基本日志、指标或链路追踪能力。
- 已明确可收集的信息范围，避免泄露敏感数据。
- 性能测试或 CI 执行中能访问必要的观测平台或导出数据。

## 本阶段范围

### Metrics

- 服务 CPU、内存、磁盘、网络等基础资源指标。
- 接口响应时间、吞吐、错误率、超时率。
- 数据库、缓存、队列和第三方依赖指标。
- 自动化执行维度的通过率、失败率、耗时和 flaky 趋势。

### Logs

- 自动化执行日志。
- API 请求响应摘要，避免记录敏感字段。
- 服务端错误日志和关键业务日志。
- UI 控制台日志、网络错误和截图。
- 已知错误和排查结论沉淀到 `harness/known-errors.md`。

### Trace

- 核心链路请求 ID 或 trace ID 透传。
- 跨服务调用耗时和错误节点定位。
- 性能测试中慢请求的链路追踪。
- 自动化报告中关联 trace 或日志查询入口。

## 实施步骤

1. 统一自动化执行中的用例 ID、请求 ID 和 trace ID 记录方式。
2. 梳理 P0/P1 核心链路需要查看的指标、日志和 trace。
3. 在测试报告中增加日志、截图、请求摘要和 trace 关联信息。
4. 建立常见失败分类和排查路径。
5. 将重复问题沉淀到 `harness/` 文档。
6. 和性能测试结果对齐，形成瓶颈定位流程。

## 产物

- 观测字段规范。
- 自动化报告关联信息规范。
- 常见失败排查流程。
- 性能问题定位流程。
- 已知错误和 flaky 用例沉淀文档。

## 验证方式

- 使用一次真实或模拟失败，验证能从测试报告定位到日志和 trace。
- 使用一次慢请求，验证能关联到指标变化和调用链。
- 抽查报告中是否包含足够上下文且不暴露敏感信息。
- 复盘排查耗时是否比纯手工查日志更短。

## 完成标准

- P0/P1 失败报告能提供定位所需的核心上下文。
- 常见失败能按分类进入固定排查路径。
- 性能问题能关联指标、日志和 trace。
- 敏感字段有脱敏或不采集策略。

## 暂不处理

- 建设完整 APM 平台。
- 对所有系统做全量 trace 改造。
- 在没有数据治理前采集完整请求响应正文。
- 将观测平台告警作为第一阶段硬门禁。
