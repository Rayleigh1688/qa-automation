# P2 完整回归

## 阶段目标

建立完整回归自动化集合，用于发版前、夜间任务或专项回归，提升覆盖面和版本信心。

## 前置条件

- P0 和主要 P1 用例已经稳定。
- 已有标签、分组、报告和失败定位能力。
- 测试环境能承受较长时间自动化执行。
- P2 场景有明确取舍，不把低价值场景无限扩张。

## 本阶段范围

### API

- 低频业务路径和非核心配置组合。
- 异常路径、边界值、兼容历史数据和批量操作。
- 跨模块联动场景。
- 历史缺陷、线上告警和客服反馈沉淀出的回归场景。

### UI

- 低频但高可见度的页面流程。
- 关键页面兼容性、空状态、错误状态和权限缺省状态。
- 不同角色、不同配置下的主要页面展示。
- 发版前需要人工检查的页面，优先转成可自动验证的断言。

### 框架

- 支持夜间、发版前、手动触发等不同执行模式。
- 支持长耗时任务的超时、重试、失败归档和分批执行。
- 优化报告聚合，区分 P0/P1/P2 失败影响。
- 建立用例准入和淘汰机制，避免回归集膨胀失控。

## 实施步骤

1. 汇总手工回归清单、历史缺陷和线上问题。
2. 按风险和维护成本筛选可自动化场景。
3. 为 P2 用例增加标签、模块、负责人和执行频率。
4. 分批补充自动化，优先 API，必要时补 UI。
5. 接入夜间任务或发版前任务。
6. 定期清理低价值、长期不稳定或业务已下线的用例。

## 产物

- P2 完整回归清单。
- 夜间或发版前执行配置。
- P2 自动化用例集合。
- 回归报告和趋势记录。
- 用例准入、降级和淘汰规则。

## 验证方式

- 至少完成一次完整 P2 回归执行。
- 检查长耗时任务是否能稳定产出报告。
- 抽查失败分类是否能区分真实缺陷、环境问题、数据问题和脚本问题。
- 对比手工回归清单，确认高价值场景未遗漏。

## 完成标准

- P2 回归可按需执行，不阻塞日常开发提交。
- 报告能清楚展示模块、优先级和失败原因。
- 长期 flaky 用例不影响 P0/P1 门禁判断。
- 完整回归集合有明确维护机制。

## 暂不处理

- 无业务价值的穷举式组合测试。
- 对不稳定第三方系统的强依赖回归。
- 未形成稳定环境和数据准备方式的场景。
