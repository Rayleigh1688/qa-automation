# P1 重要业务自动化

## 阶段目标

在 P0 稳定后扩展重要业务模块自动化，覆盖高频操作、关键业务规则、权限差异和历史高风险问题，减少版本回归中的人工重复验证。

## 前置条件

- P0 自动化已稳定运行，并具备统一执行、报告和失败定位能力。
- P1 业务模块已有明确优先级、业务规则说明和测试数据来源。
- 已确认哪些场景适合 API 覆盖，哪些场景必须通过 UI 验证。
- 已建立已知问题和 flaky 用例记录机制。

## 本阶段范围

### API

- 重要业务模块的 CRUD、状态流转、筛选查询和导出类接口。
- 业务规则组合校验，包括权限、额度、状态、时间窗口和配置开关。
- 关键异常路径，包括参数缺失、越权、重复提交、状态冲突和边界值。
- 历史线上问题对应的回归用例。

### UI

- 重要业务页面的主路径操作。
- 表单校验、列表查询、详情展示、状态提示和关键弹窗。
- 权限差异下的菜单、按钮和可见字段。
- 只保留能代表用户真实操作风险的 UI 场景。

### 框架

- 按模块建立标签和执行分组，支持单模块回归。
- 增强测试数据工厂，减少用例之间的数据耦合。
- 补充业务规则说明，沉淀到 `skills/business-rules.md`。
- 建立历史问题回归标签，便于按缺陷来源追踪。

## 实施步骤

1. 盘点 P1 模块清单，按风险、频率和历史缺陷排序。
2. 为每个模块确定 API/UI 覆盖边界。
3. 先补 API 用例，再补必要 UI 用例。
4. 将业务规则、边界条件和权限矩阵沉淀到文档。
5. 将 P1 用例接入分组执行和报告。
6. 每轮执行后整理 flaky、环境问题和真实缺陷。

## 产物

- P1 模块自动化清单。
- 模块级 API 自动化用例。
- 高价值 UI 自动化用例。
- 业务规则和权限矩阵文档。
- 历史问题回归用例集合。
- 模块级执行报告。

## 验证方式

- 每个 P1 模块至少完成一次独立执行。
- 抽查关键业务规则的断言是否与产品或业务口径一致。
- 对历史问题用例进行人工复核，确认能防止同类问题回归。
- 检查 P1 用例是否可按模块、标签、优先级单独执行。

## 完成标准

- 高风险 P1 模块均有 API 自动化覆盖。
- 必要 UI 场景有稳定用例，且不重复验证大量 API 已覆盖规则。
- P1 用例可独立分组执行并输出清晰报告。
- 业务规则和历史问题已沉淀到对应文档。
- flaky 用例有处理状态，不长期混入稳定用例集合。

## 暂不处理

- 低频配置组合的全量覆盖。
- 跨浏览器、跨设备完整矩阵。
- 长时间运行的批处理和异步任务全链路验证。
- 性能、容量和稳定性压测。
