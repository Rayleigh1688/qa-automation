# Xmind测试用例

人工在Xmind中编写、评审用例，AI按已确认的前置、步骤和预期执行测试，再把明确批次的结果回填到一份新的导图。默认生成从左到右的逻辑图：需求／模块 → 用例 → 前置条件、步骤、预期等字段，可在Xmind客户端展开、收起。

当前已实现纯离线模板、CSV导出、Xmind导入和结果回填。导入只产生用例定义及来源定位，不生成或覆盖`plan.json`，不登录、不运行API/UI，也不将自然语言步骤转换为可执行代码。测试执行继续使用[现有流程](testing-workflow.md)，需要人工确认预期、明确环境及本轮操作范围；已有执行计划按原编号和授权使用。

## 四个命令

输出文件或目录必须尚不存在，原Xmind、用例及实测结果保留。

```bash
# 生成可人工编辑的向右逻辑图，内含TC-001、TC-002示例
npm run qa:xmind -- template --out reports/qa/xmind-demo/template.xmind --title 测试用例

# 从已有总表导出导图；读新版总表时只提取用例定义，不继承登记状态
npm run qa:xmind -- export --cases requirements/ISOP-2100/cases.csv --out reports/qa/xmind-demo/ISOP-2100.xmind --title ISOP-2100

# 导入人工编写的导图，目标为新的目录
npm run qa:xmind -- import --input reports/qa/xmind-demo/template.xmind --out reports/qa/xmind-demo/imported

# 将本批明确结果回填到新的导图；只做离线关联和展示
npm run qa:xmind -- fill-results --input reports/qa/xmind-demo/template.xmind --results reports/qa/xmind-demo/result.json --out reports/qa/xmind-demo/results.xmind
```

`template`和`export`的`--title`可省略。`fill-results`可增加`--cases <本批冻结cases.csv或cases.json>`核对用例定义；源导图内容有改动时先复核本批定义，不把旧结果套到修改后的前置、步骤或预期上。结果文件须来自实际执行或明确整理的批次，模板和导入成功不产生业务PASS。

## 人工怎么写

用例节点写成`[TC-001] 用例名称`，也兼容`TC-001 用例名称`。每条编号唯一，保留稳定编号；模块可分多层，字段放在用例的直接子节点。字段值选用“字段名：内容”或字段名下的逐条子节点，后者保留编写顺序与嵌套层级；没有节点值时也可使用字段节点的纯文本备注。

```text
测试用例
└─ 代理后台
   └─ [TC-001] 按日期查询代理统计
      ├─ 类型：UI
      ├─ 前置条件：使用本地配置中的测试角色；已有本批样本
      ├─ 测试数据：本批测试代理引用、选定日期范围
      ├─ 操作步骤
      │  ├─ 1. 打开代理统计页面
      │  └─ 2. 选择日期范围并查询
      ├─ 预期结果：范围内统计与独立来源一致，范围外数据不计入
      ├─ 级别：高
      └─ 验收点：填写已确认需求点编号
```

支持的字段及别名：

| 字段 | 写法与默认值 |
| --- | --- |
| 类型 | `API`、`UI`、`FLOW`；省略时为`UI`，层级不决定执行方式 |
| 前置条件 | 也支持`前置`；必须明确，确实无需额外前置也写明“无额外前置条件” |
| 测试数据 | 可选；导入时与操作步骤合并到`参数/步骤`，不放真实凭据或个人资料 |
| 操作步骤 | 也支持`参数/步骤`、`步骤`；必须明确 |
| 预期结果 | 也支持`预期`；必须明确，执行前确认 |
| 级别 | 也支持`优先级`；省略时为`中` |
| 验收点 | 也支持`需求点`；省略时为`未关联`，随后人工补齐需求映射 |
| 模块/接口 | 可显式填写；省略时继承用例上方的模块路径 |

没有明确的前置、步骤或预期时拒绝导入，不用默认文案补成完整用例。同一字段及其别名不能重复填写。导入校验编号、字段及层级结构，不判断业务预期正确，也不检查页面或接口是否存在。模板使用占位示例；实际数据通过本地fixture或脱敏样本别名引用，密码、token、证件及未脱敏资料继续留在忽略配置或证据目录。

字段标题后的值、纯文本备注及下级节点同时存在时，按该顺序合并；步骤／预期子节点的纯文本备注也保留，嵌套层级用缩进表示。富文本、图片或附件中的业务预期需要另行人工阅读，不从图片内容推断断言。

## 导入产物与执行衔接

| 文件 | 用途 |
| --- | --- |
| `cases.csv` | 兼容原九列`FIELDS`：用例编号、类型、模块/接口、用例名称、前置条件、参数/步骤、预期结果、级别、验收点 |
| `cases.json` | 同一组九字段用例列表，便于冻结、核对和回填；属于定义，不是执行计划 |
| `source.json` | 原导图路径、SHA256及sheet/topic定位，用于追溯导入来源 |
| `README.md` | 本次导入说明和后续操作边界 |

CSV沿用现有防公式转义：以`=`、`+`、`-`或`@`开头的单元格会加单引号。JSON保留原始正文，回填时可核对原始JSON或这份CSV。

先检查导入清单与原图一致，再按[团队分工](team-testing.md)确定API执行资产或人工UI清单。现有API配置仍需显式实现请求、断言、账号与业务写范围；导入`类型：API`不会自行取得执行能力。未接入统一计划的用例可由AI在本轮明确目标、已确认预期及授权范围内定向执行，结果按导入编号留证据。

可先用现有报告命令离线校验：

```bash
npm run qa:report -- --cases reports/qa/xmind-demo/imported/cases.csv
```

同一批次选择一份设计源维护，Xmind修改后重新导入新目录。导出CSV为人工交换格式；不会同步改写需求Markdown、总表、团队包或活动任务。采用导图前先明确该批次的设计源，避免同时手工维护两份步骤和预期。

## 结果回填

结果沿用[四状态及JSON协议](testing-workflow.md#四种结果)：`PASS`、`FAIL`、`NOT_RUN`、`ERROR`。顶层须有`results`列表，可携带`run_id/environment/source_time/mode`描述批次；每项使用`id/status/actual/evidence/category`。所有结果须有实际结果或未执行原因，非`NOT_RUN`须有证据引用；源证据先脱敏。

结果按精确Case ID关联；重复编号、未知编号或不支持的状态会拒绝回填。缺结果的用例保持`NOT_RUN`，源导图已有PASS也不当作本批实测。业务验收编号与API数据组合的执行编号不自动映射，也不按行号、名称或父模块匹配；一条组合通过不表示整条验收通过。若实测结果使用执行编号，先选对应冻结用例及明确结果范围，人工评审覆盖后再形成业务用例结论。

回填写出新的`.xmind`，保留用例内容与原始导图。结果节点供阅读，不能替代原始JSON、截图、请求响应及本批报告；重新回填应明确选定来源，不从多个批次中自动挑选PASS。
