## 一次测试的六步

| 步骤 | 产物 | 完成条件 |
| --- | --- | --- |
| 1. 明确范围 | Story、环境、负责人、选定用例 | 用户确认本轮测试；已有明确授权不重复询问 |
| 2. 评审与准备用例 | questions.md、功能test-cases.md、总表cases.csv及已有API数据表 | 人工确认业务规则、功能预期及API断言；总表功能在前/API在后，数据组合关联稳定编号 |
| 3. 检查前置 | preparation.csv | 数据、角色、接口/页面、定位就绪；缺项只影响相关用例 |
| 4. 先冒烟后验收 | 每条用例的断言结果 | 失败记录后继续独立用例；仅停止依赖失败状态的后续步骤 |
| 5. 查看结果 | results.html、results.csv | 结果树、失败点、证据可直接查看；不等AI分析才出结果 |
| 6. 确认缺陷 | 失败用例归并后的BUG清单 | 按授权查重、创建或复用、关联Story并回读；再向提测发布群发一条汇总，见[缺陷交付](telegram-qa.md#bug-delivery) |

## 用例怎么写

人读的评审入口是questions与[功能用例模板](../requirements/_template/test-cases.md)：先看短名称，再看前置、步骤、预期和待确认。总表使用[总用例模板](../requirements/_template/cases.csv)，按功能/API分组，展示登记状态与负责人。具体数据组合通过[API数据表](../requirements/_template/api/data-cases.csv)关联总用例；实际请求与机器断言以执行JSON为准，CSV供审阅，不直接执行。数据准备见[前置清单模板](../requirements/_template/preparation.csv)。

- API：按文档的方法、参数、类型、必填和边界准备正反例，独立请求、独立断言。跨账号/多步状态流单列FLOW，不要求每个单接口用例重跑全链。
- UI：提测前按需求/设计/原型列预期；提测后由人工核对实际页面，补齐可直接操作的步骤，不要求编写自动化定位。页面实现不能反过来定义预期。
- FLOW：只验证关键业务顺序、状态和副作用。fixture准备、登录和清理是执行阶段，不充当业务用例PASS。
- 表格不放凭据、真实身份数据、长响应和调试过程。通过本地fixture引用和证据文件关联。
- 预期必须在执行前确定。未知长度/权限契约的用例列NOT_RUN及原因，不用观察到的行为临时定义PASS。

## 人工确认预期与断言

2026-10-03用户明确：功能测试预期和接口测试断言需要人工确认，AI在目标明确后加快执行。产品文档本身可能有错误，简体版保留原文及版本关联，翻译之外的规则澄清单独记录。

- 人工确认计算公式、统计范围、状态、时间归属、权限和异常副作用；金额、报表等规则结合可复算样例评审，不能只确认文字与原文一致。
- API配置逐项展示请求数据、HTTP响应码、业务码／信息、响应字段及业务副作用断言；记录对应功能用例、确认人、日期和规则／配置版本。确认记录放在该需求questions或evidence-sync中，不新增第二套权威规则。
- AI补充的预期及断言先作为待评审建议；未确认部分保持NOT_RUN及原因，不据此判断产品PASS/FAIL。执行按已确认版本进行，保留断言结果及证据；公开报告按现有脱敏规则显示预期和实际，不承诺展示完整业务响应。
- 已确认且内容未变的范围沿用原确认；规则或断言发生实质变化时，只复核受影响部分。来源hash和离线检查通过均不等于人工确认业务正确，也不等于业务测试通过。

此处是执行流程约定，本次未新增执行器的程序校验。功能用例模板仍按用户先写首版、助手补充、共同定稿推进；不将本段替代用户模板。

现有统一计划已支持配置HTTP响应码、`body.status`、响应信息和字段的相等、包含、类型、数量等断言；业务副作用须显式编写步骤与断言。旧查询配置保留各自支持的检查项，不能直接混用两种格式。JMeter／Postman导出尚未选型或实现；简体需求版本的测试空间及首份来源尚待明确，尚未形成转换发布流程。

## 四种结果

| 状态 | 判定 | 反馈 |
| --- | --- | --- |
| PASS | 操作有效，全部预定断言通过 | 一句实际结果 |
| FAIL | 操作有效，产品行为违反预期 | 哪个断言；预期是什么；实际是什么 |
| NOT_RUN | 未执行，或缺前置导致业务断言未被覆盖 | 缺什么，影响哪些用例 |
| ERROR | 脚本/定位/解码等执行故障，未形成有效产品结论 | 执行故障点，不直接创建产品BUG |

结果和缺陷分类分开：FAIL可以是PRODUCT候选、CONTRACT或待分析，不自动等于一个BUG。一个BUG可关联多条失败用例。准备阶段和调试次数不计入业务通过数。

服务端返回500等实际响应属于已观察到的结果，按预期判FAIL；没有有效响应或脚本异常需要区分ERROR。定位不到元素不能直接判产品FAIL；有证据证明入口缺失、控件被遮挡等违反需求时才判FAIL。

## 避免反复折腾

- 正式执行不顺便调试定位。一次失败留下日志和截图，转入独立排障阶段；修正脚本后另开记录复测。
- 不自动重放写请求。只有已知异步状态允许在用例声明的时间内轮询；轮询不是再次提交。
- 业务失败停止依赖链并保留现场；其他独立用例继续。恢复权限等清理放finally，单独记录是否恢复成功。
- 按本轮明确选择统计，不把未选择、未执行、执行错误算通过。不以减少BLOCKED或追求通过率为目标。
- 测试过程不发群；反馈只说本批范围、四种状态数量、失败清单和下一步缺项。详细请求、响应、截图展开查看。

## 文件与执行入口

每个需求在自己的`requirements/<Story>/`目录维护两类用例，不混合不同Story，也不把参数矩阵堆进总表。

| 文件 | 读者与内容 | 维护源 |
| --- | --- | --- |
| `questions.md` | 供人评审的问题和答复 | 按问题维护决定及来源 |
| `test-cases.md` | 供人评审的功能用例：短名称索引、前置、步骤、预期和待确认 | 人工维护卡片，旧宽表兼容；格式见[文档约束](../requirements/document-style.md#功能用例的阅读顺序) |
| `api/test-cases.md` | 独立API用例设计，保留编号及就绪缺口 | 有真实设计才创建；不代表已有执行资产 |
| `cases.csv` | 总表：功能在前、API在后，新版含登记状态、负责人及验证方式 | 合并功能与API设计后自动生成，不展开数据组合 |
| `api/data-cases.csv` | API数据驱动审阅表：执行编号、总用例编号、数据集、变量、请求/步骤、预期/断言和就绪情况；包含API实现的后台FLOW | 从已有`plan.json`或旧`api/cases.json`生成，不凭设计文档造执行资产 |

JSON仍是执行器输入，CSV不是第二份手工维护源。`plan.json`导出的请求/步骤及预期/断言来自`review`文字，不是全部机器步骤和`expect`的逐项展开；评审需同时核对执行JSON，修改配置时同步review。旧`api/cases.json`的数据表会列出request、expect和checks。没有API执行资产的需求只导出总表，显示“API未实现”，不创建虚假的可执行数据。模板中的API示例也不代表真实路由可运行。

总用例编号例如`ISOP-2027-C04`，关联多个图片边界执行编号；数据表和执行结果保留原执行编号。`--only`接收执行编号，不接收总表编号；同一总用例的一条组合PASS不代表整条验收完成。新版总表以“功能/API”显示分类，验证方式单列；跨API/UI功能在执行端仍使用FLOW，执行模型和人工回填格式不变。旧九列CSV继续可读。ISOP-2022保留原R01—R31编号，以所在需求目录区分，不重新编号；移出范围项会明确标注。

总表状态是用例文档已登记的状态，不是自动汇总的最新实测。执行完成度需结合明确批次、环境、版本和证据查看；导出总表不产生PASS，也不自动把API结果覆盖为功能结果。`qa:report`读取新版总表时只提取用例定义，未提供本批结果仍为NOT_RUN。

```bash
# 为指定需求生成总表和已有API数据表，全程离线
npm run qa:cases -- ISOP-2100
# 更新全部当前需求，不遍历历史目录；没有API资产时只生成总表
npm run qa:cases -- --all
# 历史兼容示例：显式指定已归档需求，仅更新生成表，不恢复执行授权
npm run qa:requirement -- ISOP-2027 --export-cases
```

`preparation.csv`继续记录前置。执行报告仍逐条记录本批展开后的组合与失败点，使用本批cases.snapshot.json；不能按行号把展开后的执行结果拼到业务总表中。新增业务用例也不自动成为旧冻结计划的已覆盖项。已有团队包的manual.csv/packet.json及最近实测不因用例视图调整被覆盖。

```bash
# 只检查用例结构；不登录、不运行测试
npm run qa:report -- --cases requirements/ISOP-2100/cases.csv
```

`qa:requirement -- <Story> --rebuild <实测目录>`可从仍存在的原始结果及冻结用例离线重建视图；已退出的历史目录不能重建或充当最新证据。

结果JSON格式：顶层`run_id/environment/source_time/mode/results`；results每项`id/status/actual/evidence/category`。id必须属于CSV且不能重复；非NOT_RUN必须有证据引用，所有状态必须有实际结果或原因。历史整理使用`mode=historical-summary`，页面明确显示未重新测试。缺结果的用例自动NOT_RUN。

统一执行/团队入口默认输出`results.csv`与`results.html`，原始结果和冻结快照另外保留。`--extra-views`按需增加cases/failures/pending CSV与summary.json；旧`qa:report`及查询CLI的六份视图继续兼容。报告命令退出0表示生成成功，不表示测试通过。

现有`run-requirement-api.py`已自动附加`views/`结果树与CSV，原result.json/report.md和退出码保留兼容。声明式UI执行器已区分动作/定位ERROR与明确断言FAIL，Telegram聚合遇到ERROR不判PASS，也不把它交给产品FAIL分析。UI和受控业务旧执行器尚未全部自动适配结果树；统一输出使用本模块，逐步接入，禁止再复制每轮session.py报告逻辑。Jira状态通知脚本不在本次调整范围。
