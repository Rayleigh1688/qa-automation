## 一次测试的六步

| 步骤 | 产物 | 完成条件 |
| --- | --- | --- |
| 1. 明确范围 | Story、环境、负责人、选定用例 | 用户确认本轮测试；已有明确授权不重复询问 |
| 2. 准备用例 | 总表cases.csv + API数据表api/data-cases.csv | 总表按业务场景，数据组合通过总用例编号关联 |
| 3. 检查前置 | preparation.csv | 数据、角色、接口/页面、定位就绪；缺项只影响相关用例 |
| 4. 先冒烟后验收 | 每条用例的断言结果 | 失败记录后继续独立用例；仅停止依赖失败状态的后续步骤 |
| 5. 查看结果 | results.html、results.csv | 结果树、失败点、证据可直接查看；不等AI分析才出结果 |
| 6. 确认缺陷 | 失败用例归并后的BUG清单 | 用户确认具体BUG后整批建单关联Story，再一次性发群 |

## 用例怎么写

使用[总用例模板](../requirements/_template/cases.csv)、[API数据表模板](../requirements/_template/api/data-cases.csv)和[前置清单模板](../requirements/_template/preparation.csv)。总表写业务场景、必要边界、简洁步骤和预期；完整请求、具体数据集及机器断言只进API数据表。一个总用例可以关联多条数据组合。

- API：按文档的方法、参数、类型、必填和边界准备正反例，独立请求、独立断言。跨账号/多步状态流单列FLOW，不要求每个单接口用例重跑全链。
- UI：提测前按需求/设计/原型列预期；提测后由人工核对实际页面，补齐可直接操作的步骤，不要求编写自动化定位。页面实现不能反过来定义预期。
- FLOW：只验证关键业务顺序、状态和副作用。fixture准备、登录和清理是执行阶段，不充当业务用例PASS。
- 表格不放凭据、真实身份数据、长响应和调试过程。通过本地fixture引用和证据文件关联。
- 预期必须在执行前确定。未知长度/权限契约的用例列NOT_RUN及原因，不用观察到的行为临时定义PASS。

## 四种结果

| 状态 | 判定 | 反馈 |
| --- | --- | --- |
| PASS | 操作有效，全部预定断言通过 | 一句实际结果 |
| FAIL | 操作有效，产品行为违反预期 | 哪个断言；预期是什么；实际是什么 |
| NOT_RUN | 未执行，或缺前置导致业务断言未被覆盖 | 缺什么，影响哪些用例 |
| ERROR | 脚本/定位/解码等执行故障，未形成有效产品结论 | 执行故障点，不直接创建产品BUG |

结果和缺陷分类分开：FAIL可以是PRODUCT候选、CONTRACT或待分析，不自动等于一个BUG。一个BUG可关联多条失败用例。准备阶段和调试次数不计入业务通过数。

服务端返回500等实际响应属于已观察到的结果，按预期判FAIL；没有有效响应或脚本异常需要区分ERROR。定位不到元素不能直接判产品FAIL；有证据证明入口缺失、控件被遮挡等违反需求时才判FAIL。

## 避免反复折腾

- 正式执行不顺便调试定位。一次失败留下日志和截图，转入独立排障阶段；修正脚本后另开记录复测。
- 不自动重放写请求。只有已知异步状态允许在用例声明的时间内轮询；轮询不是再次提交。
- 业务失败停止依赖链并保留现场；其他独立用例继续。恢复权限等清理放finally，单独记录是否恢复成功。
- 按本轮明确选择统计，不把未选择、未执行、执行错误算通过。不以减少BLOCKED或追求通过率为目标。
- 测试过程不发群；反馈只说本批范围、四种状态数量、失败清单和下一步缺项。详细请求、响应、截图展开查看。

## 文件与执行入口

每个需求在自己的`requirements/<Story>/`目录维护两类用例，不混合不同Story，也不把参数矩阵堆进总表。

| 文件 | 读者与内容 | 维护源 |
| --- | --- | --- |
| `cases.csv` | 总用例：API/UI/流程的业务场景、前置、简洁步骤、预期和验收点；不展开数据驱动组合 | 同目录`test-cases.md`的业务用例表，CSV自动生成 |
| `api/data-cases.csv` | API数据驱动审阅表：执行编号、总用例编号、数据集、变量、请求/步骤、详细断言和就绪情况；包含API实现的后台FLOW | ISOP-2027从`plan.json`生成；旧需求从`api/cases.json`生成 |

JSON仍是执行器输入，CSV不是第二份手工维护源。`plan.json`中的review是执行组合描述，不能当总表；具体参数和断言变更只改执行JSON。没有API执行资产的需求只导出总表，显示“API未实现”，不创建虚假的可执行数据。模板中的API示例也不代表真实路由可运行。

总用例编号例如`ISOP-2027-C04`，关联多个图片边界执行编号；数据表和执行结果保留原执行编号。`--only`接收执行编号，不接收总表编号；同一总用例的一条组合PASS不代表整条验收完成。跨API/UI验收在总表类型中记FLOW，具体分工以业务设计及delivery为准。ISOP-2022保留原R01—R31编号，以所在需求目录区分，不重新编号；移出范围项会明确标注。

```bash
# 为指定需求生成总表和已有API数据表，全程离线
npm run qa:cases -- ISOP-2027 ISOP-2032
# 更新全部需求；没有API资产时只生成总表
npm run qa:cases -- --all
# 原入口继续兼容：更新本需求两份表及旧查询兼容数据
npm run qa:requirement -- ISOP-2027 --export-cases
```

`preparation.csv`继续记录前置。执行报告仍逐条记录本批展开后的组合与失败点，使用本批cases.snapshot.json；不能按行号把展开后的执行结果拼到业务总表中。新增业务用例也不自动成为旧冻结计划的已覆盖项。已有团队包的manual.csv/packet.json及最近实测不因用例视图调整被覆盖。

```bash
# 只检查用例结构；不登录、不运行测试
npm run qa:report -- --cases requirements/ISOP-2027/cases.csv
# 从最近真实执行的原始结果及冻结用例重建精简视图，不登录
npm run qa:requirement -- ISOP-2027 --rebuild reports/qa/ISOP-2027/20260911T050501Z-d626392b
```

结果JSON格式：顶层`run_id/environment/source_time/mode/results`；results每项`id/status/actual/evidence/category`。id必须属于CSV且不能重复；非NOT_RUN必须有证据引用，所有状态必须有实际结果或原因。历史整理使用`mode=historical-summary`，页面明确显示未重新测试。缺结果的用例自动NOT_RUN。

统一执行/团队入口默认输出`results.csv`与`results.html`，原始结果和冻结快照另外保留。`--extra-views`按需增加cases/failures/pending CSV与summary.json；旧`qa:report`及查询CLI的六份视图继续兼容。报告命令退出0表示生成成功，不表示测试通过。

现有`run-requirement-api.py`已自动附加`views/`结果树与CSV，原result.json/report.md和退出码保留兼容。声明式UI执行器已区分动作/定位ERROR与明确断言FAIL，Telegram聚合遇到ERROR不判PASS，也不把它交给产品FAIL分析。UI和受控业务旧执行器尚未全部自动适配结果树；统一输出使用本模块，逐步接入，禁止再复制每轮session.py报告逻辑。Jira状态通知脚本不在本次调整范围。
