# 跨团队Agent协作：参考项目与讨论顺序

研究日期：2026-09-23。当前阶段是需求澄清与方案讨论，尚未确定交互平台、数据格式或运行框架，未实现发送和自动处理。

[需求入口](../requirements/README.md) · [问题写法](../requirements/document-style.md) · [2104问题示例](../requirements/ISOP-2104/questions.md)

## 已有共识

- 测试侧先把问题写清楚：短名称、场景、问题点、需要确认的事项，来源和影响用例可追溯。
- Agent先查资料、补上下文和整理文档；需要业务取舍的内容再以简洁中文交给人。
- 产品Agent的业务决策权限由产品负责人定义。测试侧核对答复是否有依据、是否足以形成测试预期。
- 双方分别维护自己的专业职责；每一步先研究确认，再开始实现。

## 这与服务治理有哪些相似之处

以下是针对本项目的分析：跨团队Agent需要知道“对方是谁、能处理什么、可以读写什么、任务交给谁、何时算完成、失败后怎么继续”。这对应服务发现、身份权限、任务路由、超时重试和审计。

需求澄清还需要管理事实、建议与决定。任务技术上完成，只能说明收到了答复；是否解决业务疑问，要检查来源、授权范围及具体结论。外部资料和对方消息是待核对内容，不直接扩大本方操作权限。

## 值得研究的项目

这些项目分处通信、执行和协作平台等层面；可以借鉴设计，不必一起引入。

| 项目 | 官方已提供的能力 | 与本项目最相关的借鉴 | 采用前仍要解决 |
| --- | --- | --- | --- |
| [A2A](https://github.com/a2aproject/A2A) | 跨Agent能力描述、消息、任务和产物 | 一条问题作为可追踪任务，答复与文档修改建议作为交付物 | 业务权限、证据标准、问题字段、各方实际接入能力 |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | 有状态Agent编排、持久化、人工介入 | 查证、补问、等待产品、恢复处理等明确步骤 | 服务部署、持久存储、对外通信和跨团队身份 |
| [Temporal](https://docs.temporal.io/workflow-execution) | 工作流历史、持久执行、消息和恢复 | 等待数小时/数天后继续，记录重试和超时处理 | Agent能力本身、用户界面、业务判断及运维投入 |
| [GitHub Issues/Webhooks](https://docs.github.com/en/webhooks/about-webhooks) | 议题记录和事件通知；表单可规范输入 | 问题编号、讨论记录、修改审阅及收到答复后的触发 | 如何路由到正确Agent、重复事件、哪些答复有权成为决定 |

### A2A：任务怎样跨Agent交接

官方将Agent能力描述、工作任务、过程消息和结果产物分开，分别为Agent Card、Task、Message、Artifact；结果可以带文本、文件或结构化数据。[核心概念](https://a2a-protocol.org/v1.0.0/topics/key-concepts/)

任务支持等待输入等状态；已结束任务的后续工作应建立关联的新任务。等待输入不天然意味着等待产品本人，接收角色需要业务层明确。[任务生命周期](https://a2a-protocol.org/v1.0.0/topics/life-of-a-task/)

权限判断由服务实现负责，协议不决定产品Agent能代表谁作决定。[授权职责](https://a2a-protocol.org/v1.0.0/specification/#75-server-authorization-responsibilities)

成熟度：官方已有[v1.0.1发布](https://github.com/a2aproject/A2A/releases/tag/v1.0.1)，本次阅读使用1.0.0规范。应按选定版本实现并验证互通；协议版本本身不证明本项目接入稳定。

### LangGraph：何时停下，怎样继续

interrupt可保存状态并等待外部输入，以同一线程标识恢复。恢复时节点会从头执行，暂停前的副作用需要特别处理。[人工介入与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

本项目可借鉴“先保存问题和依据，再等答复”的做法。业务操作应与推理步骤明确分开，防止恢复一次就重复发评论或修改文档。它适合组织一个Agent内部的流程；跨团队协议和授权仍需另行约定。

### Temporal：长时间等待和失败恢复

Signal传入异步消息，Update可校验请求并返回处理结果，Query用于只读查看状态。[消息传递](https://docs.temporal.io/encyclopedia/workflow-message-passing)

本项目可对应为“收到产品答复”“确认答复已受理”“查看当前等谁”。它的持久工作流能力适合长时间等待；外部写入仍需用唯一标识防重，Activity可能重试，不能推定发评论只发生一次。[Activity幂等说明](https://docs.temporal.io/activity-definition#idempotency)

### GitHub：可审阅的协作记录

Issue Forms用YAML定义输入项并生成Issue正文；官方文档当前仍标为public preview，因此可参考其表单设计，不能把它当不可变的机器协议。[表单说明](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)

Webhook可驱动收到事件后的处理；官方建议核对事件类型、校验来源、快速应答后异步处理，并利用delivery标识识别重复投递。[Webhook实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

对于本项目，GitHub适合作为正式问题和修订的候选记录平台；Telegram可以作为通知入口。这是待讨论的职责划分，尚未选定平台，也没有发送授权或实际投递。

## 先用六个场景研究流程

| 场景 | 应得到的结果 | 下一次讨论要确认的点 |
| --- | --- | --- |
| 已有答案，本地文档落后 | 具体来源、对应条款、建议修改 | 谁核对并接受补丁？怎样确认来源没有过期？ |
| 文档互相矛盾 | 冲突两边、适用版本、影响例子 | 对方Agent能否在授权内确定采用依据？什么时候转产品本人？ |
| 缺接口或可核对的记录 | 实现说明、交付版本、正常范例记录 | 转产品Agent还是开发Agent？怎样记录已转交？ |
| 需要产品取舍 | 简短中文问题、选项影响、明确决定 | 谁答复有效？决定覆盖哪个版本、哪些场景？ |
| 无人应答或对方暂时不可用 | 可见的等待状态、重试或提醒记录 | 等多久提醒？最多来回几轮？怎样避免重复发送？ |
| 已确认后规则再次变更 | 新版本决定及受影响用例 | 旧决定如何保留？在途任务和测试断言怎样失效？ |

以2104 Q-02为演练例子：测试侧提供“已过门槛、投注1000、比例1%、封顶5”的问题，产品Agent先查页面规则是否已有结论；若只能找到派发规则，就带着缺口提交给产品。收到页面显示决定后，测试侧核对答复版本并同步C03；这一过程不自动证明用例通过。

## 人和Agent怎样读取同一条问题

AI也可以读中文。机器版本主要需要稳定字段、明确身份和来源版本，不能靠增加术语来替代结构。

建议先保持questions.md为当前维护入口。未来机器版本由确定版本的文档生成，记录来源文件及版本；它是交互材料，避免两份内容分别手工维护。若后续改为结构化文件作为主源，需要单独确认迁移及人工编辑方式。

| 信息 | 人读时 | Agent交接时需要补充的结构 |
| --- | --- | --- |
| 问题 | 短标题、具体场景、请确认什么 | Story ID、Question ID、问题修订版本 |
| 已知与未知 | 问题点和已有答案 | 已确认事实、缺口、推测分别记录；绑定来源及读取时间 |
| 接收方 | 产品或开发 | 团队、Agent身份、能力、允许操作与转人工角色 |
| 答复 | 中文结论与理由 | 对应问题版本、答复类型、来源、答复者、授权依据 |
| 更新结果 | 已确认或继续待答 | 受影响Case、建议补丁、应用记录与验证状态 |

这些只是待审字段分类，还不是JSON Schema或消息协议。尤其“建议、引用已有决定、产品新决定、请求补充资料”应有可区分的答复类型，不能用一段自由文本混为一谈。

## 文件与运行记录的候选职责

| 内容 | 候选位置/职责 | 需要先确认 |
| --- | --- | --- |
| 人读的问题与决定 | 继续在requirements各需求的questions.md | 何时接收答复并更新，谁负责核对 |
| 双方约定的格式与流程 | 在docs下维护独立协作说明；协议定义另行定路径 | 单仓库还是共享协议仓库，版本如何协商 |
| 每次发出的机器材料 | reports下按需求和修订保存生成快照 | 哪些内容可跨团队发送、保留多久 |
| 收发、等待、重试和人工决定 | 使用持久状态存储，并关联现有工作流 | 复用现有状态库还是独立服务；哪个是状态权威 |
| 通知 | GitHub/Telegram等适配器 | 正式记录在哪里、消息怎样回到原问题、发送权限 |

日常任务可以先研究“检查来源变化、整理待问项、投递澄清、核对答复、生成文档修订、提示长期等待”六类。每类都需明确输入、输出、触发条件、权限和停止条件；没有答复不能自动当作同意。

## 下一次讨论顺序

1. 用一个真实问题走完六种场景，先确定谁接收、谁负责作决定、输出是什么。
2. 确定正式记录和通知各放在哪里，再讨论跨仓库权限。
3. 确定人类文档与机器材料的单一维护来源、最小字段和版本规则。
4. 确定收发状态、重复消息、超时、转人工及重新打开的处理。
5. 根据前面结果选择是否引入A2A、LangGraph或Temporal，再设计一个小范围试点。

当前只完成问题文档整理和官方资料研究；以上候选方案都需要讨论后再定。
