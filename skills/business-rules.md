# Business Rules

## 用途

沉淀接口自动化必须理解的核心业务规则，避免 AI 只根据接口名或 HTTP 状态做错误判断。

## 规则

## 主流程顺序

测试用例和报告按业务流程排序，接口清单保持接口文档扫描顺序。

主流程顺序：

1. 注册登录。
2. KYC。
3. 充值。
4. 投注。
5. 派彩和投注数据检查。
6. 提现。
7. 钱包、账变、会员、VIP、活动、代理等相关数据检查。
8. 后台报表展示和审批。

## 通过标准

业务通过不等于 HTTP 200。

接口通过必须同时满足：

- HTTP 状态符合预期。
- 响应可解码。
- 业务 `status=true`。
- 响应结构稳定。
- 关键字段存在。

HTTP 200 但 `status=false` 必须判定失败，并记录原因。

## 写操作边界

写操作不是绝对禁止。注册、充值、提现这类重要主流程属于 P0，需要按“P0 主流程写操作冒烟”执行。

它和只读 P0 门禁分开，是为了避免每次快速回归都创建订单、触发第三方支付链接或冻结资金；不是因为它优先级低。

允许在 FAT 里试跑的 P0 主流程写操作：

- 新增测试用户。
- 创建测试充值订单。
- 创建小额测试提现申请。

P0 主流程写操作必须满足：

- 使用测试环境和测试账号。
- 使用最小金额或明确测试数据。
- 执行结果单独输出，不混入只读 P0 smoke。
- 记录创建的订单号、用户、账号状态，便于后台核对。
- 失败时保留业务错误，不用放宽断言。

以下操作仍默认不自动跑：

- 支付回调。
- 后台审批通过、审批拒绝。
- 后台配置新增、更新、删除、开关。
- 奖励领取、签到、补签。

这些接口只有在具备固定测试账号、可控测试资金、可回滚数据和明确断言后，才允许进入自动化。

## 前后台区别

客户端接口：

- 主要验证玩家视角主流程。
- 当前 P0 优先只读链路和登录前置。
- token 放在 `t` header。

后台接口：

- 主要验证运营、财务、KYC、报表和审批视角。
- 当前只纳入只读接口。
- 登录需要真实浏览器请求同款 header，尤其是 `x-device-id`。
- Google code 必须按数字发送。
- token 使用裸值放在 `t` header，不加 `t:` 前缀。

## 当前 P0 业务覆盖

客户端已覆盖：

- OTP 登录前置。
- KYC 详情和 eKYC 配置。
- 充值渠道、充值记录。
- 游戏首页、列表、推荐、最近、历史、投注记录、收藏。
- 提款账户、银行列表、提现 tab、提现记录。
- 钱包、账变、会员详情、VIP 配置、代理基础信息。

后台已覆盖：

- 当前登录用户详情。
- 银行卡列表。
- 账变类型。
- KYC 待审批数量。
- eKYC 配置。
