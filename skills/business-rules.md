# Business Rules

## 用途

沉淀接口自动化必须理解的核心业务规则，避免 AI 只根据接口名或 HTTP 状态做错误判断。

## 主流程顺序

测试用例和报告按业务流程排序，接口清单保持接口文档扫描顺序。

主流程顺序：

1. 注册登录。
2. KYC。
3. 充值。
4. 投注。
5. 派彩和投注数据检查。
6. 提现。
7. 上述行为完成后的相关数据检查，以及后台报表展示和审批。

KYC 是 P0 主流程，必须 UI + API 双验证。UI 证明真实新账号或已驳回账号能完成 KYC 页面提交并出现成功提示；API 证明提交后的前台状态、后台待审/审核记录和审核后状态刷新。`KYC successful` 只表示提交成功等待处理，不等于已审核通过。

## 通过标准

业务通过不等于 HTTP 200。

正例接口通过必须同时满足：

- HTTP 状态符合预期。
- 响应可解码。
- 业务 `status=true`。
- 响应结构稳定。
- 关键字段存在。

反例通过必须证明接口按预期拒绝：HTTP 状态、业务错误、响应结构和无副作用均符合场景断言。HTTP 200 但 `status=false` 不能作为正例通过；只有反例明确预期该业务拒绝时才可通过。

## 写操作边界

写操作不是绝对禁止。测试环境的注册、充值、提现和必要后台审核属于 P0 受控主流程。`python3 scripts/run-api-tests.py p0` 默认执行 safe/negative，并将资金链推进到充值和后台补单检查点；后续真实投注、流水核对和提现按 `api/p0/README.md` 的跨执行面放行规则继续。`--safe-only` 只执行只读和安全反例。

允许自动执行的受控写操作：

- 新增测试用户。
- 创建测试充值订单。
- 创建专用测试提现申请。
- 对本次专用充值/提现单执行后台补单、审核同意和成功标记。

P0 主流程写操作必须满足：

- 使用测试环境和测试账号。
- 使用专用测试账号、明确金额和受控数据。
- 资金主流程使用同一普通会员完成不参加活动的充值、投注和提现；普通存款基础流水在提现前完成，主链路不主动验证流水限制拒绝。
- 充值页面的 `Multiple Deposit Bonus` 活动开关默认不参加；参加活动会产生提现流水限制。
- 所有充值都会产生普通存款基础流水；`rotation_flag=0` 只表示不叠加活动流水，`rotation_flag=1` 表示在基础流水上叠加活动规则。
- 提现正例账号必须无活动流水限制、已 KYC、已绑定提款账户且可提现余额充足。
- 审核动作使用真实审批 TOTP；后台登录固定码不能替代审批码。
- 执行结果保留独立原始 JSON，并汇总到主流程报告。
- 记录创建的订单号、用户、账号状态，便于后台核对。
- 失败时保留业务错误，不用放宽断言。

以下操作仍默认不自动跑：

- 支付回调。
- 后台配置新增、更新、删除、开关。
- 奖励领取、签到、补签。

这些接口只有在具备固定测试账号、可控测试资金、可回滚数据和明确断言后，才允许进入自动化。

KYC 探索使用 `090XXXXXXXX` 测试账号池，首个账号从 `09000000001` 开始；测试环境 OTP 固定为 `111111`。已驳回或未通过 KYC 的账号可以再次提交，减少账号池消耗。`9888888050` 已知存在提现流水限制，除非后台先解除限制，否则不要作为提现正例账号。

## 前后台区别

客户端接口：

- 主要验证玩家视角主流程。
- token 放在 `t` header。

后台接口：

- 主要验证运营、财务、KYC、报表和审批视角。
- 只读报表和列表为常规覆盖；仅本次专用测试单可进入受控审核动作。
- 登录需要真实浏览器请求同款 header，尤其是 `x-device-id`。
- Google code 必须按数字发送。
- token 使用裸值放在 `t` header，不加 `t:` 前缀。

## 覆盖状态来源

具体场景、接口、自动化状态和已知缺口只维护在 `api/p0/main-flow-scenarios.csv` 与 `AI-HANDOFF.md`。本文件只维护跨接口都成立的业务判断规则。
