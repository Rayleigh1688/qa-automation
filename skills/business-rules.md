# Business Rules

数据库只读评审与取数前先查[核心表参考](../docs/database/README.md)：包含结构查询模板、登录秒级时间与充值/注单毫秒的区别；字段注释和实测口径分开记录。

## 用途

沉淀接口自动化必须理解的核心业务规则，避免 AI 只根据接口名或 HTTP 状态做错误判断。

## 模块规则与复用

涉及相关模块先读已确认规则，在需求中引用编号、版本和适用差异，不从历史失败文案重新推导预期。

- 首页BI/报表统计：先读[首页模块复用入口](../modules/admin/home-bi/README.md#后续需求复用入口2026-09-29)的当前口径摘要，涉及细节再查2092决定及2190分类分母来源；报表间的时间、精度、过滤及聚合规则须确认适用性。
- [KYC编辑、复核与空集规则](business-rules/kyc.md)：字段权限、状态注入目的、实现映射与证据边界。
- [代理三套后台](../modules/agency/README.md)：服务与身份分别定位，直属关系与邀请链分开，按精确UID核主档、统计拆行、筛选和导出；业务口径与日期观察分别读取。其他关联模块见[模块索引](../modules/README.md)。

后续模块同样记录编号、适用范围、来源/日期、预期、用例/断言和验证边界。跨需求规则在本目录维护；需求特有验收留需求用例，环境问题留环境手册或harness，原始运行证据留reports。

2026-10-16按用户决定，长期保留常用规则、已有可导入能力和操作方法；低频需求从归档索引或对应Jira按需回查。归档不删除已被P0或兼容CLI使用的实现，也不自动将历史专项加入门禁。一次性账号准备、特定厂商接入及页面效果不为归档另建通用执行器。

## 主流程顺序

测试用例和报告按业务流程排序，接口清单保持接口文档扫描顺序。

主流程顺序：

1. 注册登录。
2. KYC。
3. 充值。
4. 投注。
5. 派彩和投注数据检查。
6. 钱包、账变及前后台核对。
7. 提现。
8. 后台报表及主流程总核对。

KYC 是 P0 主流程，必须 UI + API 双验证。UI 证明真实新账号或已驳回账号能完成 KYC 页面提交并出现成功提示；API 证明提交后的前台状态、后台待审/审核记录和审核后状态刷新。`KYC successful` 只表示提交成功等待处理，不等于已审核通过。

## 通过标准

业务通过不等于 HTTP 200。

正例接口通过必须同时满足：

- HTTP 状态符合预期。
- 响应可解码。
- 业务 `status=true`。
- 响应结构稳定。
- 关键字段存在。

反例通过必须证明接口按预期拒绝：HTTP 状态、业务错误、响应结构和无副作用均符合场景断言。HTTP 200 但 `status=false` 不能作为正例通过；只有反例明确预期该业务拒绝时才可通过。

## 写操作边界

写操作不是绝对禁止。测试环境的注册、充值、提现和必要后台审核属于 P0 受控主流程。API 独立组合包含后台清流和提现，完整 API+UI 组合包含真实投注；两者证据范围不同。具体命令范围统一见 [命令说明](../docs/commands.md)。

允许自动执行的受控写操作：

- 新增测试用户。
- 创建测试充值订单。
- 创建专用测试提现申请。
- 对本次专用充值/提现单执行后台补单、审核同意和成功标记。

P0 主流程写操作必须满足：

- 使用测试环境和测试账号。
- 使用专用测试账号、明确金额和受控数据。
- 资金主流程使用同一普通会员完成不参加活动的充值、投注和提现；普通存款基础流水在提现前完成，主链路不主动验证流水限制拒绝。
- 完整验收可在用户明确指定时采用“固定投注次数 + 管理后台清空剩余流水”：Playwright 必须先实际完成指定次数并证明流水下降；后台清流必须由独立显式参数开启，并分别记录投注后剩余流水和清流后最终流水，不能把管理动作表述为投注自然完成。
- 充值页面的 `Multiple Deposit Bonus` 活动开关默认不参加；参加活动会产生提现流水限制。
- 所有充值都会产生普通存款基础流水；`rotation_flag=0` 只表示不叠加活动流水，`rotation_flag=1` 表示在基础流水上叠加活动规则。
- 提现正例账号必须无活动流水限制、已 KYC、已绑定提款账户且可提现余额充足。
- 未 KYC 提现反例固定使用永久保持 BASIC/未提交状态的 `PRE_KYC_CLIENT_PHONE`，不得将该账号用于 KYC 提交；KYC 最小闭环使用独立的 `KYC_CLIENT_PHONE`。
- 最低提现金额使用有效提款账户通过 API 传入小于通道最小值的金额验证；不要用低余额账号替代金额下限场景。客户端 UI 只需证明合法金额能够提交并生成本次提现订单。
- FAT 仅登录验证码允许使用固定 `111111`。登录完成后的所有业务验证码，包括审核、资金调整、充值倍率、流水、VIP、风控、启停及其他写操作，必须使用当前实时 Google TOTP；后台登录固定码不得代替业务验证码，也不得用来重试失败的业务请求。
- 执行结果保留独立原始 JSON，并汇总到主流程报告。
- 记录创建的订单号、用户、账号状态，便于后台核对。
- 失败时保留业务错误，不用放宽断言。

以下操作仍默认不自动跑：

- 支付回调。
- 后台配置新增、更新、删除、开关。
- 奖励领取、签到、补签。

这些接口只有在具备固定测试账号、可控测试资金、可回滚数据和明确断言后，才允许进入自动化。

账号分配、FAT/UAT 验证码和环境差异统一见 [环境手册](../api/runbooks/ENVIRONMENTS.md)；具体账号状态仅保存在忽略的本地配置中。

## 前后台区别

客户端接口：

- 主要验证玩家视角主流程。
- token 放在 `t` header。

后台接口：

- 主要验证运营、财务、KYC、报表和审批视角。
- 只读报表和列表为常规覆盖；仅本次专用测试单可进入受控审核动作。
- 登录需要真实浏览器请求同款 header，尤其是 `x-device-id`。
- Google code 必须按数字发送。
- token 使用裸值放在 `t` header，不加 `t:` 前缀。
