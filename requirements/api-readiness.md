# 从需求预期到接口评估与固定回归

2026-09-14，按用户要求补充测试准备标准。[流程](workflow.md) · [状态列表](status.md) · [2028实际示例](history/through-ISOP-2072/ISOP-2028/design.md#接口能力预期与当前评估)

目标是让测试能发现“接口虽成功，但业务能力不满足需求”。AI负责拆规则、找遗漏、设计可区分对错的数据、编写确定性断言与固定代码；需求答案由明确来源和已确认决定约束，不能让实际接口输出反过来定义预期。

## 需求出来时就准备什么

在design.md中建立“接口能力预期与当前评估”，先写业务能力，不猜URL、方法或数据库字段。每行关联验收点与Case ID，并区分需求明确要求、AI设计建议、待确认事项。比如“异步导出能获得完整文件并确认结束”是能力要求，具体用MQTT还是轮询是待核对的实现选择。

| 准备项 | 需要回答的问题 | 产物与完成依据 |
| --- | --- | --- |
| 需求基线 | 来源版本是什么？角色、范围、金额/时间规则、排除项与兼容要求是什么？ | design.md记录来源，questions.md记录缺项及最终决定 |
| 接口能力预期 | 查询、提交、读回、异步结果分别需要什么能力？输入能否表达业务条件，输出能否支撑页面和核验？ | design.md能力对照表；允许复用旧接口，不要求一条需求对应一个新接口 |
| 数据与独立预期 | 怎样得到已知非空样本和应有金额？正常/异常状态如何准备、清理、隔离？ | preparation.csv引用样本方案与Case；真实标识保存在忽略的本地fixture，不提交个人资料 |
| 数据链路 | 源记录如何进入聚合表、API和导出？有无迁移/历史回填、时区、精度、刷新延迟？ | 相关需求补充api/data-review.md；无数据库依赖则注明不适用及替代证据 |
| 测试设计 | 正例、反例、边界和状态组合能识别哪些具体错误？拒绝是否确实无副作用？ | test-cases.md业务场景；提测后映射plan.json的具体参数与断言 |
| 可测条件 | 各角色账号、依赖服务、可观察的任务完成状态、样本生成和恢复是否具备？ | preparation.csv逐项标明就绪/缺失/不适用及影响Case，不以全局待确认拦住独立项 |
| 回归环境 | FAT/UAT的地址、登录、角色、样本、数据链路及版本如何对应？ | 环境能力核对记录；不把FAT数据ID复制到UAT，不只替换域名 |

## 怎样设计高有效性的正反例

每条高风险业务规则至少有一个能区分正确与错误实现的样本。空列表、全零金额或只有一种类型的数据，通常无法证明筛选、公式和分组正确。

| 维度 | 正例与反例设计 | 关键断言 |
| --- | --- | --- |
| 输入与边界 | 合法最小/最大值、边界内外、缺失/null/空串、错误类型、非法枚举、开始时间大于结束时间 | 精确的业务接受/拒绝规则，不能仅断言“不是200”；未定义规则先列问题 |
| 数据筛选 | 同窗口同时准备应命中与应排除记录，使用不同金额/类型，含空窗口和跨页 | 应有记录集合、无不该出现记录、总数/合计、字段映射；无数据只证明空结果契约 |
| 权限 | 未登录、无效凭据、有效但无权限角色、其他用户/线路的对象 | 拒绝及无数据泄露/业务变化；鉴权失败不能代表数据隔离已验证 |
| 写入与状态 | 合法迁移、非法前态、重复提交、失败重试、适用的并发冲突 | 提交结果+权威读回+副作用检查，不能只看成功响应；仅操作本轮专用记录 |
| 金额与时间 | 非零、负值、精度边界、跨日、跨月、结算与投注时间不同、时区边界 | Decimal独立计算、明确舍入层级/包含边界和统计时间依据 |
| 异步/导出 | 接收任务、任务失败、分片/分页、结束、超时、重复片；非空与空文件 | 关联本轮任务，有限等待，完整文件的表头、顺序、集合和金额；ok不代表导出完成 |
| 兼容与影响 | 旧默认参数、旧数据、关联列表/汇总/导出、可选字段 | 新能力有效，同时原约定行为未被破坏；变更需求时修订基线并保留来源 |

优先覆盖资金、权限、跨日、幂等、聚合与异步等实际风险；不机械穷举所有参数笛卡尔积。每个反例说明“会抓到哪种错误”。可用本地夹具验证断言能抓住漏一条、错一分钱、重复一次、越权一条等错误；夹具通过只证明测试代码，不证明产品通过。每条生产回归用例必须能追溯到业务Case，避免仅镜像实现。

## 数据库什么时候需要对比

涉及新增字段、金额统计、状态持久化、多表关联、数据迁移/回填或排程刷新时，需要核对受影响的数据结构及链路。纯文案/布局且没有数据契约变化的需求无需全库结构比较。数据库只读，先看DDL/元数据与有界样本，不以直接写库准备状态。

| 对比内容 | 要检查什么 | 不能据此推出什么 |
| --- | --- | --- |
| 结构 | 需求前后DDL/迁移说明、FAT/UAT受影响表或视图；字段类型、精度、小数位、默认值、可空性、唯一约束、关联键，必要索引/分区 | 字段存在不等于程序已正确写入；结构不同不一定是BUG，需关联需求 |
| 语义映射 | 需求字段→源字段→聚合表达式→API/导出字段；金额符号、状态枚举、时间单位/时区 | 列名相似或注释相同不等于语义相同 |
| 数据与聚合 | 固定样本集合与截止点，去重/分组/过滤，刷新延迟、历史回填范围和完成标识 | 两个读取同一错误聚合表的接口相等，不是独立正确性证据 |
| 可用性 | 只读权限、快照/查询时点、环境一致性、可接受刷新期限 | 无法查库是证据缺口，不自动认定功能失败 |

在api/data-review.md保留对比日期、环境、版本、涉及对象、脱敏结构差异、查询模板/摘要、结论和影响Case。有明确可验证的API输入/权威流水时可作为独立预期来源，无需强依赖数据库。缺少独立来源时保留结构测试，但业务对账不得记为已验证。

## 提测后必须给出的功能评估

api/contract-review.md逐行映射“能力预期→实际接口/版本→已有证据→差异→Case”。检查不仅限于字段：还要看输入是否能表达需求、权限隔离、读回、异步完成、导出、历史数据与运行条件是否足够。

design.md只维护简明结论和证据链接，详细差异留在评审文件：

- **契约覆盖结论**：满足 / 部分满足 / 不满足 / 待确认，写明范围与缺少的能力。
- **本轮可测性**：可测Case、不可测Case及具体原因；准备就绪不等于测试通过。
- **实测功能结论**：已验证满足 / 发现不满足 / 尚未验证，按能力分别记录并链接批次。不要把一个总标签遮住已测与未测范围。
- **回归交付结论**：固定代码/计划范围、FAT/UAT分别是否实际验证、剩余手工项和环境缺口。

即便契约写得完整，也只能说明设计覆盖；需实测才能评估实现。接口缺能力时先说明受影响的需求及最小补齐内容，建议实现方式与需求硬性要求分开。BUG提交沿用用户确认流程。

## 测过以后怎样固化为一键回归

测试设计、数据和代码在首轮执行前开始落地；首轮发现问题后补强断言，修复后保留相同用例复验，再稳定纳入回归。固定执行不依赖AI临场猜参数、从报告抽取“正确答案”或手工改脚本。

沿用plan.json、共享业务方法和统一CLI；业务Case→参数组合→断言→结果可追溯。样本准备/检查、业务执行、读回、恢复、报告形成固定过程；失败保留证据，恢复失败单独报告。可独立运行、可重复运行，不依赖上次token或其他人的订单；已知失败用例也保留，不能删掉以获得绿色结果。

每个需求api/README.md登记已交付范围、环境支持、准备要求、命令与最近验证证据。回归验收包括：本地有意义的断言测试、FAT实际运行、针对可重复性的第二轮验证、UAT独立配置与实际验证。受控写入按既有范围启用，不默认扩大写范围。新需求不自动加入P0。

当前已有入口示例（FAT，只读计划）：

```bash
# 离线校验
npm run qa:requirement -- ISOP-2028 --export-cases
# 真实测试，输出独立批次
npm run qa:requirement -- ISOP-2028 --env .env.fat --execute --insecure
```

**当前能力边界：**代码核对发现requirement_adapter仍固定FAT，requirement_readonly的合规地址固定FAT，客户端登录只支持该密码路径。现有新计划尚不能宣称可一键UAT回归。下一步需实现环境/服务地址配置、UAT动态登录、环境对应样本及防串环境校验，再做独立UAT实测；此文档没有修改这些运行限制。其他既有P0/旧CLI的环境能力按各自入口判断，不能互相代替。

## 本轮落地与后续

本轮更新设计/接口评审模板，新增数据核对模板，以2028补写能力预期及评估。其他已存在需求尚未逐项补齐，不视为已经完成这套评审；2022仍按用户要求暂停实测。优先用2028补公式/数据/导出有效性，再按状态表推进其他需求，FAT/UAT回归能力按代码和真实环境证据分别交付。
