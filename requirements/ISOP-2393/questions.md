## 问题详情

<a id="q-01"></a>
### Q-01：会员端输入精度与文案规范

**场景：** 后台弹窗明确要求小数两位，但会员端仅说明需大于0（PHP、不设最小/最大值），未说明会员端是否限制小数两位、最大输入位数、非法值提示文案及`Daily loss limit`替换后的完整页面文案。

**需要确认：** 会员端输入校验规则、错误提示及确认弹窗正式文案。

**答复：** 待确认。

<a id="q-02"></a>
### Q-02：存量`Daily loss limit`数据兼容

**场景：** 需求将`Responsible Gaming`页的`Daily loss limit`改为每日投注上限。

**需要确认：** 上线前已设定过`Daily loss limit`的存量会员，原有数值是清空重新设定、保留作废还是迁移为每日投注上限。

**答复：** 待确认。

<a id="q-03"></a>
### Q-03：进入游戏阻挡入口边界

**场景：** 当日投注额大于或等于每日上限时，会员进入游戏需阻挡并提示固定英文文案。

**需要确认：** 阻挡是否覆盖所有游戏启动接口（真实投注、各厂商进入游戏、最近游玩、收藏直连等），试玩模式是否豁免，以及接口返回的错误码约定。

**答复：** 待确认。

<a id="q-04"></a>
### Q-04：取消上限弹窗校验规则

**场景：** 正文在「设定／修改弹窗」说明原因必填、最多200字、未填提示`請輸入原因`，在「取消上限」处仅写原因必填。

**需要确认：** 取消上限弹窗是否同样限制最多200字及相同提示文案，以及确认弹窗交互细节。

**答复：** 待确认。

<a id="q-05"></a>
### Q-05：Filbet站与后端/后台排期范围

**场景：** 父单覆盖两站。复读子任务已确认 FilPlay H5 `ISOP-2398`、FilPlay App `ISOP-2399`、管理后台 `ISOP-2400`、后端 `ISOP-2401`；Filbet 客户端交付安排仍待核实。

**需要确认：** Filbet 各客户端由哪条任务负责，两站客户端、管理后台与后端计划如何对应。

**答复：** 待确认。

<a id="q-06"></a>
### Q-06：原型、Figma与附件截图核对

**场景：** 父单附带后台原型及两版共 6 张截图，`ISOP-2398` 附带 Figma 链接（`node-id=4788-15064`）及 7 张 H5 截图。已获取清单，视觉内容尚未核对。

**需要确认：** 下载附件并打开原型与Figma核对字段顺序、金额格式、倒计时格式、提示语及分页控件。

**答复：** 待核对。

<a id="q-07"></a>
### Q-07：进游戏阻挡弹窗文案差异

**场景：** 父单`ISOP-2393`写明进游戏阻挡提示`You have reached your daily betting limit. Please try again tomorrow.`；子任务`ISOP-2398`写明弹窗文案`You have reached your daily betting limit.`，含`OK`与`View Settings`按钮。

**需要确认：** 正式上线采用哪版提示文案（是否保留`Please try again tomorrow.`），以及App（`ISOP-2399`）与Filbet是否保持一致。

**答复：** 待确认。

<a id="q-08"></a>
### Q-08：次日调整与`Remove`交互差异

**场景：** 父单`ISOP-2393`描述次日起可「调高、调低或取消」，调整后立即生效且当日再次锁定；子任务`ISOP-2398`仅描述次日`Remove`按钮恢复可点击、点击后直接移除设置（未提直接修改数值及移除是否二次确认）。

**需要确认：** 客户端次日是否允许直接修改数值，还是必须先点击`Remove`移除后再重新设定；点击`Remove`是直接生效还是需二次确认。

**答复：** 待确认。

<a id="q-09"></a>
### Q-09 后台写请求怎么编码，哪个值代表取消

两个后台 Bruno 模板都写 `body: none`，参数位于说明。取消示例写 `is_cancel: 0`，旁注写 `1` 取消。请提供设置和取消各一份脱敏的实际请求契约，包括请求体编码、字段类型、必填项、编辑权限标识和拒绝业务码。对应 A04、A05、A10。

<a id="q-10"></a>
### Q-10 后台金额、来源和日志分页的字段契约

后台读文档的 `limited_bet_amount` 示例是布尔值 `true`，上限需要显示 PHP 金额。历史列表只展示操作和金额示例，缺设置来源、操作者身份来源和分页字段。请明确状态与历史各字段、关闭及取消后的空值、来源枚举、初次写入如何映射操作，以及每页 10 条由服务端还是客户端负责。对应 A02、A06。

<a id="q-11"></a>
### Q-11 会员取消后当天能否重新设置

会员在次日主动取消时，父单同时写到当日锁定与关闭后可重新设置。请确认当天取消之后的首次重设是否接受，以及关闭状态下 `edit_countdown` 的值。会员仅受后台取消影响和会员主动取消的场景应分别确认。对应 A03、A07。

<a id="q-12"></a>
### Q-12 游戏拦截接口和日统计就绪证据

父单要求当日投注额 `>=` 上限时拦截进游戏。四笔提交只更新限投配置读写文档。请明确两站各端实际使用的游戏入口、拒绝业务码、可核对的会员日统计字段以及刷新完成信号或有效等待上限。对应 A08、A09。

<a id="q-13"></a>
### Q-13 两站 FAT 部署版本、地址和角色

FB 接口文档远端 `main` 已确认，Jira App 子单显示 FAT 测试。请分别确认 Filbet、Filplay 的 FAT 版本、对应域名与专用角色／账号。端侧文案和编辑交互另见 [Q-07](#q-07)、[Q-08](#q-08)。

<a id="q-14"></a>
### Q-14 金额的精度和空值怎么序列化

父单规定会员输入大于 0 且无业务最小值、最大值，后台要求两位小数。请明确会员输入精度、可声明的存储范围，以及后台超两位小数是否拒绝或如何处理。请同时确认会员保存关闭时的金额字段传法。对应 A03、A04、A10。
