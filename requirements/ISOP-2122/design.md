# ISOP-2122：测试设计

[设计](design.md) · [问题](questions.md) · [测试重点](test-cases.md) · [W26评审](../reviews/2026W26-20261006.md)

直入桌台、同游戏大厅降级及原账务统计不变的目标已明确，公开API也已明确`hall=SEXY`。轮盘A01支持清单、扩展码解析、降级分类和账务身份仍待确认。本目录整理2026-10-06已读来源及W26评审，本次未重新读取远端来源、未执行业务测试，也未接入执行计划。

## 范围与明确规则

| 项目 | 当前规则与依据 |
| --- | --- |
| 入口表达 | Jira使用`基础游戏码:桌号`表达新增桌台入口，例如`roulette:A01`；扩展同厂商游戏码唯一性限制下的入口配置。例子不等于已确认可用桌号。 |
| 直入参数 | 调用`doLoginAndLaunchGame`并传桌台参数。公开API v1.0.06 §5.3明确`hall=SEXY`，另外传`platform`、`gameType`、基础`gameCode`、`isLaunchGameTable=true`和`gameTableId`；§7.8列SEXYBCRT为LIVE。`hall`不能取roulette等游戏码。 |
| 长度与默认值 | API§5.3规定`gameTableId`最长10字符，`isLaunchGameTable`默认false；附件24200的后台厂商游戏码字段总长50字符。扩展码解析与旧码兼容见[Q-02](questions.md#q-02)。 |
| 桌台失败 | Jira要求返回对应游戏大厅网址，例如轮盘桌台失败回轮盘大厅；不以任意厂商大厅或空地址替代。错误降级分类见[Q-03](questions.md#q-03)。 |
| 原有账务与统计 | Jira要求保持原统计、回调和注单写入，不按桌拆投注记录；不新增按桌报表。新增入口身份与基础账务身份的关联见[Q-04](questions.md#q-04)。 |
| 启动URL | API§5.3规定启动URL十分钟有效且只能使用一次，`url`与`extension`备用URL择一使用；降级不能重复消费同一URL。 |
| 启动频率 | API§7.10规定同玩家每秒最多一次，建议额外留1—2秒处理余量；降级请求同样需遵守。 |
| 桌台状态 | API§5.10的`getLobbyState`提供桌台维护状态，可用于准备有效与关闭桌台样本。 |

## 来源差异与影响

| 来源对照 | 影响及关联 |
| --- | --- |
| Jira示例`roulette:A01`；公开API§7.6只列Baccarat Classic的1—10／C17—C22和Extra Sicbo的131／132，没有轮盘A01。 | 需冻结本期实际支持版本与基础游戏码／桌号映射，不把示例直接作为成功样本，也不据公开列表直接断言轮盘不受支持，关联[Q-01](questions.md#q-01)。 |
| 原始厂商码与带冒号桌号的扩展码共同存在；总码50字符与桌号10字符是不同约束。 | 解析、字符和大小写校验影响旧入口与落地桌，关联[Q-02](questions.md#q-02)。 |
| API§7.4已列维护1047、无效游戏1033、超时1040、认证1027、账号锁定1013／暂停1014等结果。 | 已有错误码不能自动决定平台降级策略，特别是账号和认证拒绝；同游戏大厅取URL方式需遵守单次使用与频率合同，关联[Q-03](questions.md#q-03)。 |
| 新增平台入口拥有扩展码，厂商回调仍需按基础游戏身份定位。 | 入口可区分不代表账务按桌拆分；原回调去重和聚合必须保持，关联[Q-04](questions.md#q-04)。 |

待确认正文与答复统一放在[问题与决定](questions.md)。后续测试核实际落地桌台、同游戏大厅降级、旧入口及原钱包／注单／报表一致性，详见[初步测试设计](test-cases.md)。
