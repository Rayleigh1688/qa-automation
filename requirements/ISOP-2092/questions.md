### Q-01：选上周或上月，图表到底显示哪段日期？

**答案（09-28核对用户指定原型）：** 以点击当天为基准，“上周”展示此前5个完整自然周，不含本周；“上月”展示此前6个完整自然月，不含本月。周一开始、周日结束。

| 2026-09-28点击项 | 原型图表日期 | 粒度 / 点数 |
| --- | --- | --- |
| 上周 | 2026-08-24—2026-09-27 | 周 / 5个点，周起点为08-24、08-31、09-07、09-14、09-21 |
| 上月 | 2026-03-01—2026-08-31 | 月 / 6个点，03—08月 |

**180天问题（最新）：** 用户明确外层统计少于90天、内层图表最多180天，两套规则分别验收。原型默认完整六个月可能超过180天，记录为默认配置与限制不协调，不据此要求后端豁免180天。

**历史实测（09-26，FAT）：** 上周图表带入08-17—09-20；按原型规则，该点击日的前5个完整周恰为此范围，因此这一日期观察与原型一致。上月带入03-01—09-30，包含7个月，与原型不符。接口180天可查、181天拒绝，本月/上月默认窗口失败（F08）；历史失败不因本次原型核对改为通过。

**来源与边界：** 用户09-28提供的[原型](https://vip-admin-gray.vercel.app/admin)，实际操作“上周/上月→总投注”查看日期框、默认粒度、横轴和表格。截图及页面文字见本地忽略目录`reports/qa/ISOP-2092/20260928-prototype-q01/`。本次仅核对该原型的两个默认窗口，未刷新Jira/Confluence、未复测FAT/UAT、未验证其他点击日期或自定义限制。原型仍显示注册率，不能据此覆盖2092已有的注册率移除等其他规则。

### Q-02：首充过了当天，再充值还算复充吗？

**场景：** 会员昨天完成首充，今天又充值一笔；首充定义为用户注册后的第一笔 Completed 充值。

**问题点：** 新文档写“非首充”，可能包含这笔；既有TLSQ-78产品评论只算首充当天的非首充订单。

**当前结论（09-29最新核定）：** 用户再次核对后明确复充金额取数据库gt>1，gt=0和gt=1均排除；保留Completed、会员提交、首次充值时间为统计当日条件。此决定替代此前gt!=1解释，不把“非首充”泛化为所有gt!=1。

**验证边界：** 对现有09-29源单/API证据离线复评，89/89日复充金额一致；09-09应2400实际2400，09-23应100实际100。SRC01改PASS，TEST-3201按口径更正撤回并转已完成，评论17493说明无需修复；无新增业务请求，不称为代码修复回归。此次只确认金额，不扩大人数统计结论。

<a id="q-03"></a>
### Q-03：查看多天数据时，人均收入怎么算？

**场景：** 同一会员连续两天登录，运营查询这两天的ARPU（人均收入）。

**问题点：** 新需求不提供跨日登录/投注人数，这两项沿TLSQ-78显示“--”；但新版人均充值/ARPU使用“此区间”描述，与TLSQ-78六类跨日指标显示“--”仍有差异。2026-09-25实测快捷周/月六项为“--”，自定义两日却返回登录/投注人数及人均指标，已记录独立失败，不能由实现反推新规则。

**实测已核实（09-26）：** 单日ARPPU=充值金额÷充值人数，ARPU=充值金额÷登录人数；09-25分别为1200÷1=1200、1200÷8=150。两日仍返回结束日人数、三日起隐藏；两日分支及月图累加人均值已记为失败。单日分子和分母不再待确认。

**答案（09-28）：** 人均收入只提供单天数据，超过一天展示`--`。ARPU/ARPPU按此验收，快捷周/月与自定义两天及以上一致；不再讨论跨日分母累加或去重。跨日登录/投注人数沿既有`--`规则。两日返回数值和月图累加人均值仍须按明确预期回归，不自动改判通过。

<a id="q-04"></a>
### Q-04：派彩里是否已经含免费旋转和奖池奖金？

**场景：** 一段日期内既有普通投注派彩，也有免费旋转（FS）和奖池（JP）奖金，需要核对总派彩及GGR。

**问题点：** 需求要求包含三类金额；原实现使用 `net_amount` 回推派彩，未覆盖正确的三类统计口径。

**当前口径（09-29用户纠正）：** 数据库只有投注额与玩家净盈利，使用`bet_amount + net_amount`回推派彩，覆盖全部bet_type，并按既有需求加jp_winning总和。撤回此前“不使用net_amount回推”的解释；不再要求全量独立win字段作为执行前置。09-29已按该口径对账，89日中4日存在差额，见[最新复测](verification-20260929-full.md)及TEST-3203；JP加工与源同步根因仍待定位。

**已补依据（2026-09-25重新读取Jira）：** 总/分类GGR不分bet_type合计net_amount并计入jp_winning；FS GGR取bet_type=2的net_amount（公司视角），JACKPOT Winning取bet_type=3的jp_winning。

**实测已核实（09-26）：** FS按bet_type=2的-net_amount转换为公司视角，JP按bet_type=3的jp_winning汇总，87个单日与接口一致。FS/JP字段与上述符号映射不再待核。

**09-28用户重申的组2规则：**

| 指标 | 验收口径 |
| --- | --- |
| 总投注 / 有效投注 | 分别汇总bet_type=1、3的投注金额 / 有效投注金额 |
| 总派彩 | 包含一般注单、FS、Jackpot；不分bet_type回推注单派彩，使用bet_amount + net_amount回推，再按需求加jp_winning总和，核实JP不重复计入 |
| 总GGR / GGR% | 不分bet_type汇总net_amount，并加jp_winning总和；GGR%=GGR÷投注额，以百分比展示 |
| 投充比 | 有效投注金额÷充值金额，以百分比展示 |
| FS GGR | bet_type=2的net_amount合计，确认是公司角度 |
| JACKPOT Winning | bet_type=3的jp_winning合计 |

**处理：** “是否包含”及上述公式已明确，关闭业务提问。物理源字段正负号、独立派彩回推及Doris加工仍由QA/开发对账；历史MySQL符号观察不覆盖需求公式。F04/TEST-3178在[09-28回归](verification-20260928.md)已确认总GGR与七类合计差额为0，不能继续写成当前未修复；该回归未证明源单全链路对平。

<a id="q-05"></a>
### Q-05：充值、提现和投注各取哪个金额字段？

**场景：** 看板计算“充提差=充值−提现”和“投充比=有效投注÷充值”。

**问题点：** 公式已明确，公式中的金额实际对应哪些订单字段和统计范围尚待核对。

**已补依据（2026-09-25）：** TLSQ-78评论16500规定Completed存款到账金额、Completed提现金额；多日累加，投充比先汇总分子分母再计算。2092最新正文规定有效投注合计bet_type=1、3。实际页面投充比为百分比，6285÷1200展示523.75%，单位已核，不属于金额放大BUG。

**实测已核实（09-26）：** Completed充值的到账字段为paid_amount，86/87日对平，8月及9月累计对平；充值总额不直接取所有订单amount。首页充提差为充值−提现，投充比为有效投注÷充值×100；三组累计可重算，详情却错误使用总投注作分子（F07），该差异不再属于待定义公式。

**剩余技术核验：** 07-03充值差240、提现当前源状态与Doris历史统计差额、部分注单入库/修订范围仍需核；这不是让产品重新定义公式。由QA/开发查具体订单、入库时间及统计加工。F07/TEST-3179与月图F10/TEST-3176在[09-28回归](verification-20260928.md)已通过，原09-26观察只保留为历史证据。

<a id="q-06"></a>
### Q-06：除数为0或结果有多位小数，显示什么？

**场景：** 所选日期内充值为0，投充比无法正常相除；或者计算结果有超过两位的小数。

**已补答复（09-28）：** 比例数据默认显示`0.00%`；结合本题零分母场景，比例无可计算结果时也按此默认值验收。零金额仍显示整数`0`。Q-03规定的跨日人均指标显示`--`，不能用比例默认值覆盖。

**已确认（09-26纠正范围）：** 零金额显示整数 `0`；用户本次确认比例可以保留小数，`0.00%`不判失败。09-26保存的2092需求正文没有明确禁止零百分比保留小数；之前将零值补充扩大到比例，属于测试预期范围过宽。

**实测已核实（09-26）：** 零充值但存在有效投注的多个日期，basic投充比返回0；零分母ARPU/ARPPU也返回0，detail可返回空串，UI格式化为0.00。当前零分母实现行为已知；零金额显示0.00仍按此前金额规则登记；零比例0.00%不再列为格式失败。

**最终答复（09-28）：** 百分比展示到小数点后两位，第三位起直接截断，不四舍五入。例如`1.235% → 1.23%`、`1.2399% → 1.23%`；负百分比同样舍掉末位，`-1.2399% → -1.23%`（向零截断）。先按原始精度汇总、计算并换算为百分比，最后格式化展示；不得先截断比值或逐笔值再计算。

**数据边界：** 截断仅影响前端显示，不回写或降低数据库/API原始值精度。实测paid_amount为四位，申请金额及注单金额为八位，不能把数据库统一假设为四位，也不据此修改表结构。最新补充已扩展到全部数值展示，金额及人均同样向零截断两位；跨日人均仍按Q-03显示`--`。Q-06比例问题关闭，存储精度及非比例指标技术核验独立跟进。
