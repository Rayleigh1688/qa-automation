## 范围与明确规则

| 项目 | 当前规则与依据 |
| --- | --- |
| 修复场景 | 首次回调已被平台处理，但响应超时；厂商重发时余额不足，第二次返回`FUNDS_EXCEED`，平台已结算而厂商认为取消，造成9月27日差账。依据：Jira正文的复现时序与报表影响说明。 |
| 成功交易重发 | 识别已处理交易，返回处理结果并避免再次处理。余额不足不能成为已成功交易重发的拒绝理由。依据：Jira正文“回传你们的结果就好”。 |
| 余额足够重发 | [评论17487](https://alibaba-international.atlassian.net/browse/ISOP-2177?focusedCommentId=17487)指出余额足够还会再次扣款，必须同时覆盖这一风险；仅调整余额不足时的错误结果不足以证明防重修复。 |
| 原始请求特征 | 原片段为`transaction`、`action=buy_bonus`、`round_started=true`、`round_finished=false`，同时含投注和赢款。HTTP200内有业务错误，不能仅据HTTP状态判断成功。 |
| 交易与整轮状态 | 已处理交易不能直接等同整轮终结；`round_finished=false`的后续生命周期仍需保留。具体状态迁移由[Q-03](questions.md#q-03)确认。 |
| 历史处置 | 新交易防重回归与原异常订单、9月27日对账纠偏分别留证；原异常样本只读核验，不通过重放原回调制造恢复。交付范围见[Q-04](questions.md#q-04)。 |

## 合同与影响

正文已明确成功交易重发不再处理，但已读来源不足以冻结幂等键作用域、冲突载荷裁决及响应字段重放策略。待确认正文统一维护在[问题与决定](questions.md)，本设计只记录其对断言的影响。

| 依赖 | 影响范围 |
| --- | --- |
| [Q-01](questions.md#q-01) | 厂商、品牌／线路和交易`uid`的唯一性，以及同`uid`冲突载荷；同`round_id`不同合法交易不能被整轮去重吞掉。 |
| [Q-02](questions.md#q-02) | 成功响应中的余额／`version`与业务结果重放，原交易处理中时的并发行为；钱包不再变化仍不足以证明厂商不会取消。 |
| [Q-03](questions.md#q-03) | 首次真实失败、处理中、扣款后持久化异常的状态迁移，交易入账与整轮终结，以及金额单位。 |
| [Q-04](questions.md#q-04) | 历史异常订单、厂商撤销和报表纠偏的交付与对账范围；防重代码修复不能替代存量恢复证据。 |

后续测试关注钱包、派彩、账变、注单写入和厂商响应的共同一致性，详见[初步测试设计](test-cases.md)。具体字段与错误码以确认后的厂商合同为准，不从已有错误响应推导完整成功契约。
