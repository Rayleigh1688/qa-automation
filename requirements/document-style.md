# 需求文档格式约束

适用范围：所有需求的设计、问题、用例、证据同步及接口说明。2026-09-15以ISOP-2032为首版，已应用到当前班车7个需求。原始报告、接口字段、执行编号和用户原话保留原值。

## 通用写法

| 项目 | 统一规则 | 示例 |
| --- | --- | --- |
| 标题 | 一级标题为需求编号与文档用途；二、三级标题用简短中文，不混用多套序号 | `ISOP-2032：问题与决定` |
| 章节引用 | 按用户最新决定保留`§`及原文章节编号；`§`表示章节。不同文档同号时补来源或章节名称，不为排版改原文编号 | `Jira §2.3（结算与派发）`、`Lark §1—7`、`2104 §四` |
| 页面步骤 | 说明文字保持同文一致；Step1/Step2等页面标签和原文引述可保留 | `第3.3节，第3步（派发条件与弹窗）` |
| 需求编号 | 首次及跨需求链接写完整编号；同一段落中可简称 | `ISOP-2032` |
| 问题与用例编号 | 问题用`Q-01`，验收点用`AC-01`；业务用例主表保留完整ID，同需求关联可写`C01` | `Q-01、Q-05、Q-09`；范围写`Q-11—Q-13` |
| 来源及变更编号 | 已有编号稳定保留，表头用中文，并提供含义与定位；不同文件沿用旧来源别名时说明对应关系 | `来源编号`、`变更编号 / 来源` |
| 日期 | 自写日期用`YYYY-MM-DD`；来源只显示月日时写`MM-DD（页面未显示年份）`，不补造日期 | `2026-09-15` |
| 时间 | 自写完整时间用`YYYY-MM-DD HH:mm:ss（UTC+8）`；保留已有秒和毫秒精度，不为格式补造精度 | `2026-09-14 10:52（UTC+8）` |
| 并列与范围 | 并列编号用顿号，连续范围用“—”；“/”只保留给固定字段、路径或必要的组合列 | `C03、C05、C07`；`第2.1—2.6节` |
| 技术文字 | API字段、命令、路径、hash使用行内代码；产品文案及原始数据不翻译、不改拼写 | `conf`、`state`；产品文案按原文 |

## 内容和表格

- 开头先给当前结论与文档导航，详细来源和历史记录放后面；历史记录在标题或段首明确日期，不用历史“本轮”描述当前状态。
- 一行一个问题、用例或变更。单元格只写结论、必要依据和下一步；较长讨论链接到原文，不整段复制到多个表。
- 来源必须能定位到链接及章节、评论ID或接口版本；来源更新时间与实际读取时间分开。未读、已读、已同步、已验证分别说明。
- 新增问题状态使用“待确认、已确认、待核验、待同步、已合并”，答复方与状态用` / `分隔；已有“部分解决”等限定语保留，具体缺口写到处理列。确认规则不等于业务通过。
- 历史人工填写的“通过”等状态及负责人原样保留，不自动转换成API结果。业务用例及执行文件保留现有机器状态`NOT_RUN/PASS/FAIL/BLOCKED/OUT_OF_SCOPE`，不因中文排版改状态值。同步JSON也保留原枚举。
- Case ID、执行JSON、执行报告和人工回填字段保持兼容。用例卡片与新版总表由共享解析器处理，旧宽表及九列CSV继续可读；遵循[需求目录约定](README.md)。
- 无信息用“待核实”；不适用用“—”。不把未知写成“无”，也不擅自关闭问题。

## 问题文档的阅读顺序

2026-09-23按用户要求，新增或改写问题采用[问题模板](_template/questions.md)，以[ISOP-2104](ISOP-2104/questions.md)为例；当前20个需求的问题文档已完成整理，历史归档保留原记录。

- 首屏只列问题编号、简短名称、状态和答复方；名称直接说明要确认什么，避免“口径与边界”等需要额外解释的概括。
- 每个问题按“场景 → 问题点 → 需要确认”展开。先用具体操作或数字给出必要背景，再指出疑点，最后问一个能直接回答的问题。
- 无关决定拆开编号；同一规则的边界样例可放在小表里。示例明确前置，推导的金额不冒充实测，建议选项不冒充预期。
- 详细来源、用例编号和修订历史放到文末，保持问题正文易读。答复写回对应问题，并注明答复人、日期和来源。
- 原编号保持可追溯；拆分时记录从哪个问题移入，并同步设计、用例依赖和生成表。已解决的问题保留答案，不再混进待答描述。

## 功能用例的阅读顺序

2026-09-24按用户要求，以ISOP-2103、ISOP-2104试行[功能用例模板](_template/test-cases.md)。评审时先看questions，再看功能用例；其他需求暂保留旧格式。

- 首屏索引只列编号、短名称、状态和负责人，点击名称进入用例详情。
- 每条用例依次写前置条件、操作步骤、预期结果、待确认。操作分步，预期逐项，已确认预期与缺少的决定写清楚；待确认链接原Q，不重新复制问题全文。
- 优先级、验收点、验证方式以及实现说明放到后面。功能用例可以结合页面与API数据验证，分类不等于执行方式。
- 纯API用例的设计放在`api/test-cases.md`，仅在有实际设计时创建；与功能用例共享稳定编号，不重复登记同一用例。2104的C09保留编号移入该文件。
- `cases.csv`合并两处用例，功能在前、API在后，同组保留原顺序；状态和负责人来自用例登记。总表是覆盖与进度入口，具体执行结果以有批次、环境和证据的报告为准。
- 卡片只维护一份正文。索引负责状态/负责人，文末关联表负责优先级/验收点/方式；导出器校验两表与详情一一对应，缺项即拒绝导出。
- 用例正文的解析范围使用`<!-- case-cards:v1 -->`和`<!-- /case-cards -->`，详情标题保留完整Case ID；前置条件、操作步骤、预期结果、待确认四个标签保持固定。说明与历史记录放在范围外。

## 修改后检查

1. 先检查设计、问题、用例、同步记录和接口说明之间的编号、来源与状态一致性。
2. 修改用例文字后运行`npm run qa:cases -- <需求编号>`更新生成表，不手工改CSV。
3. 已登记证据基线的需求，逐项确认仅格式变化及未改变业务语义，再更新对应文件hash，记录“格式整理，未重新读取来源/未重跑业务”。
4. 运行`npm run check:docs`、`npm run qa -- evidence <需求编号> --allow-pending`及`git diff --check`。格式检查不替代来源刷新、业务测试或视觉验收。

本约束由需求入口和模板引用；当前文档检查校验链接，格式和语义仍需复核，不宣称已用程序检查全部自然语言规则。

## 目录与历史记录

- 每个需求以`design.md`、`questions.md`、`test-cases.md`为阅读入口；开头统一提供设计、问题、用例、数据与当前班车报告导航。API说明留在`api/`，不新增重复的需求README。
- `questions.md`维护答复决定，design引用决定并说明验收规则；相同整段内容只维护一处，原有锚点有引用时保留导航。
- 仍用于缺陷追溯的旧结果说明集中到[历史记录](../docs/history/requirement-records-20260907-11.md)，保留日期、来源与原始证据是否已退出；合并后更新链接并移除原零散文件。
- 当前班车记录、未关闭缺陷、2027独立FAT/UAT报告入口继续保留。原始结果、冻结计划、执行JSON、人工状态和凭据不属于文档清理对象。
- `evidence-sync.md`是长期的需求证据同步记录，已有需求才保留；不为格式统一替未核对需求生成空记录。
