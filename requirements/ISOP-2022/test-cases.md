## 执行准备与停止条件

1. 记录 FAT 部署提交/时间、需求版本与已确认答案；逐页读取当前请求，建立方法、路径、字段、时间单位、时区和响应映射。体育新表名称、主键及同步策略由代码/开发说明确认，不猜表名。
2. 凭据沿用忽略配置中的 `ADMIN_URL`、`ADMIN_EMAIL`、`ADMIN_PASSWORD`、`ADMIN_GOOGLE_CODE` / `ADMIN_LOGIN_TOTP_SECRET`。每轮重新认证，token只在内存；受限角色另用隔离账号。不要在需求文档保存账号、原始UID或截图中的用户信息。
3. 优先读取既有样本，不操作界面“重置数据/重算”来碰运气。数据不足时设计隔离夹具及官方业务造数流程，记录账号、金额、操作范围及恢复方式再执行；数据库始终只读。本轮写入金额为0、业务写入为0。
4. 复用现有认证/CBOR能力及 `scripts/qa_core/`；共享时间/集合/金额校验写为可导入模块，UI定位放 `ui/elements/`、`ui/data/`，用例放 `ui/cases/`。不修改既有npm入口/默认P0统计与报告路径。
5. 需求专用业务命令尚未实现，因此不提供虚构可执行命令。文档变更检查用 `npm run check:docs`；后续实现后先 `npm run check`，再运行明确FAT的需求专项。
6. 报告保存请求条件（脱敏）、样本标识映射、预期/实际差额、刷新时间、环境与代码版本；API原始证据进入忽略的 `api/results/`，UI进入 `ui/results/` / `ui/reports/`。保存持久证据链接后再宣称可长期追溯；当前无此链接。
7. 环境混用、未知写入、数据污染、业务拒绝、非预期完整性差额时停止相关阶段（Q-02明确接受的非体育窗口外差额单列已知限制，不阻塞本版）。区分 FAILED、BLOCKED_EXPECTATION、BLOCKED_DATA、NOT_RUN；不继续调用校准接口抹平差异。
