## 问题详情

<a id="q-01"></a>
### Q-01：实际模板是哪种奖金模式？

**场景：** 同一次FS赢额，Jira／Confluence要求立即进入钱包，PT文档Spend-only章节也如此；另一个FreeSpin示例却把奖金留在PT并附带流水及后续转账。

**问题点：** 两种模型决定不同的金额来源与结算时点，不能仅凭“FREESPIN1”名称混用示例。

**需要确认：** 本单实际PHP模板是否确定采用Spend-only即时钱包模式，并以哪份模板配置或PT确认作为验收依据？

<a id="q-02"></a>
### Q-02：可验收模板何时可用？

**场景：** 后台只传模板代码和次数，单次投注额由模板决定；PHP未配置时可能报`ERR_BONUS_TEMPLATE_NOT_FOUND`。

**问题点：** Jira保留了模板创建责任与时点待确认，当前没有可独立核对的模板参数；PT合同中的`count`为整数类型，未据此确定业务可填上下限。

**待核验：** 先查模板交付记录，取得测试环境可用的PHP模板及其单次投注额、可用游戏和次数限制；记录缺失时再向PT与运营确认提供人和时间。这是测试资料准备，不新增产品规则。

<a id="q-03"></a>
### Q-03：同模板再次派发能否领取？

**场景：** 同一玩家先后参加两个活动，或首次FS结束后再次收到相同模板的派发。

**问题点：** PT FAQ写可分配多个相同模板ID，但只能接受第一个；未说明只限制同时活跃的奖金，还是完成后的再次派发也受限。

**需要确认：** 相同模板的重复领取限制作用于什么生命周期范围？

<a id="q-04"></a>
### Q-04：旧进游戏自动派发何时退出？

**场景：** 新后台异步派发成功，玩家进入PT游戏时又可能命中原Redis配置。

**问题点：** Jira明确列出原有两个Redis键并将是否停用保留待确认；仅新增后台功能不能证明旧派发路径已停。

**需要确认：** 新流程启用时，旧进游戏自动派发路径采用什么切换方案？

<a id="q-05"></a>
### Q-05：异步发放和未知结果怎样恢复？

**场景：** 批量先建立本地记录，其中一名玩家的PT请求超时，但PT可能已受理；任务随后重启或被重试。

**问题点：** Confluence说明批量创建本身不直接请求第三方，Jira要求逐玩家异步派发；发放触发时点、未知结果的查询／重试顺序与本地状态尚无完整合同。`requestId`用于请求识别，不自动证明重复派发被PT去重。

**待核验：** 先核既有异步任务、派发关联及失败恢复合同，确认受理后超时、任务重启时怎样避免重复发放；仅缺少依据时再向后端确认。本项不指定状态枚举、队列或重试实现。

<a id="q-06"></a>
### Q-06：PT终态怎样映射？

**场景：** 玩家用完全部次数、到期、后台作废，active列表都可能不再返回该奖金；history可能延迟出现或返回Jira未列出的移除原因。

**问题点：** Jira自身待确认“用完后是否立即进history、实际removalReason”；官方枚举还有`redeemed_immediately`、`cancelled_by_expiration`等未覆盖项，不能仅依active消失判断完成。

**需要确认：** 实际模板对应的终态原因及未识别／暂不可查状态采用哪张映射表？

是否启用可选`notifyBonusEvent`也须在该同步方案中注明；未启用时不能设计依赖它的完成断言。

<a id="q-07"></a>
### Q-07：回调和轮询如何合并次数？

**场景：** 派发10次，投注回调已把已用次数更新为3；随后较早发起的active查询返回剩余8次，或同一投注回调再次到达。

**问题点：** 正文同时要求按回调增量与active剩余次数更新，缺少乱序时的合并办法，可能回退进度或重复累加。上例为设计样例，并非实测。

**待核验：** 先核既有次数更新合同及实现，确认重复／乱序回调和轮询怎样保持真实已用次数；缺少可验证规则时再向后端确认，不预设某种合并算法。

<a id="q-08"></a>
### Q-08：哪一个交易键防止重复入账？

**场景：** PT对同一GameRoundResult重试；另一个合法GameRoundResult又属于同一局。还可能出现钱包已提交、派发赢额或流水尚未提交时进程退出。

**问题点：** 官方合同要求幂等且允许一局多次结果，但Jira尚未指定本系统的唯一交易键和提交／恢复边界。仅按局号会漏掉合法派彩，分别无保护地写三处又可能重复。

**待核验：** 先核当前交易识别、钱包／派发赢额／流水写入及恢复合同，取得重复回调不重复入账、同局合法后续派彩不丢失的验证依据；缺失时再向后端确认。本项不指定数据库事务或其他实现机制。
