# 新需求测试流程

本文件是当前项目的新需求协作流程建议，用于讨论和逐步实践；不代表已实现新的执行器或 CI 门禁。目录约定与需求索引见 [README](README.md)。一个需求可以部分接口已提测、部分页面仍在设计，应按验收点记录阶段，不强制整单同步等待。

## 只有需求，前后端尚未提测

目标是把需求变成可验证的业务规则，并提前准备数据与测试方法。

1. 阅读 Jira 正文、表格、截图、评论及关联任务，记录来源版本。逐页检查字段名称、条件、计算公式、时间/金额边界、角色权限和状态流转；将明确规则与待确认项分开编号。
2. 做影响分析：哪些接口、页面、报表、异步任务、历史数据和已有回归可能受影响。旧环境可以只读摸底，但旧行为不是新需求的验收标准；未实现功能不能据此记为产品缺陷。
3. 设计业务场景，先正向主路径，再拒绝、边界、权限、重复请求和异常恢复。每条包含前置、动作、预期及副作用，映射验收点，并决定 API/UI/数据核对各负责什么。
4. 准备独立预期和数据计划：列出所需状态、角色、时间分布、金额及数据来源，盘点现有可用样本；缺少样本时记录准备方式、隔离及恢复方案。数据库只读，不直接改库造状态。
5. 在接口契约已讨论清楚时准备请求模板、测试数据构造和可复用断言；必要的离线夹具验证标注为离线结果。没有契约时先留业务场景，不猜路径、枚举或响应字段写死实现。
6. 与产品确认业务预期，与开发确认接口契约、数据迁移/任务机制、可测方式。AI可整理问题与建议修订文本；对外发评论/消息仍需用户明确授权。

交付三份相互链接的文件：`design.md`（明确规则、验收点、影响、数据/实现策略）、`questions.md`（问题、答复、最终决定）、`test-cases.md`（前置、步骤、预期、负责人、执行状态及证据）。组员领取具体Case ID；答复记录只放问题文件，答案确认后同步设计和用例。涉及明确规则的工作继续推进；只阻塞依赖未决答案的用例。此时业务执行状态是 NOT_RUN，需求评审完成不等于功能通过。

ISOP-2022 示例：先确定体育明细查询规则、非体育延迟结算完整性、时区与统计公式；规划跨日非体育、跨月体育和重结算样本。不能仅用即时结算注单证明跨日统计正确。

## 后端接口提测，前端可能尚未就绪

目标是直接验证已部署接口的业务结果，尽早发现数据与逻辑问题，不等待页面完成。

| 顺序 | 工作 | 需要留下的证据 |
| --- | --- | --- |
| 1. 核对提测范围 | 明确环境、部署版本、已交付接口及未交付项、接口契约、开发自测、已知限制；如适用核对迁移/回填/任务状态 | 本轮可测验收点与阻塞项，不只记录“后端已提测” |
| 2. 最小冒烟 | 新登录、验证权限和一条已知数据的主路径；核对编码、方法、参数类型、时间单位及返回契约 | 可解码、HTTP与业务结果、关键字段；空响应不能证明数据正确 |
| 3. 实现并执行专项 | 对照已确认契约完善可复用测试，先本地校验，再执行正向、拒绝、边界、权限、状态及适用幂等场景 | 需求→用例→实际请求→业务断言；拒绝场景检查无禁止副作用 |
| 4. 核对数据与异步行为 | 用已知样本独立核算，核对明细、汇总、关联记录、异步刷新；按适用范围验证存量与迁移 | 预期/实际差额、业务关联键、时间窗口及有界等待结果 |
| 5. 修复与影响回归 | 区分产品缺陷、契约问题、环境/数据阻塞及测试代码问题；复测修复点和受影响场景 | 修复版本、复现条件、复测证据；不为凑通过继续调用成功接口 |
| 6. 输出后端阶段结论 | 按验收点记录通过、失败、未执行及阻塞；说明哪些可进入前后端联调 | 接口阶段结论及剩余UI/联调/数据边界，不宣称整个需求验收完成 |

后端执行与复测结果写入`test-cases.md`，保留首次失败及修复后的各轮证据；新发现的需求歧义回到`questions.md`确认，不将讨论当作已通过用例。

提测信息缺失时先做不依赖它的准备，不以形式清单阻断全部工作；但不能对未知环境、未确定业务预期或无有效样本的场景给出通过。关键主路径失败时停止依赖阶段，独立只读场景可继续执行。

接口用例可以先于前端落地，契约以已确认文档与部署实现核对；前端就绪后再核对实际 Network，发现差异要查清哪一方违反约定，不能直接以任一实现覆盖需求。

ISOP-2022 示例：后端先验证结算区间筛选、体育长周期不漏单、node=0/2合并、小计/合计、物化视图刷新与历史回填；对账基准来自独立样本，不能只看几个报表互相相等。下拉框、提示文案和筛选切换留给后续UI验证。

## 前端提测到稳定回归

前端提测后验证入口、控件、字段映射、默认/重置行为、错误提示、列表/汇总展示与实际请求一致性；再用少量代表性场景完成跨API/UI业务链路。已有稳定API断言不在每个页面重复穷举。

最终按验收点汇总结论，确认修复与剩余风险，记录发布版本及证据。根据风险和维护成本将稳定用例纳入模块回归或P0；需求资料继续保留在原Jira目录，不因月份变化搬迁。具体发布决定按团队流程，不把本流程文档当成自动发布授权。
