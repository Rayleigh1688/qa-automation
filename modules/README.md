## 当前工作范围（2026-09-16用户确认）

目标是补充现有业务逻辑、落实可复用资产，支持后续新需求API测试；不要求先完成现有功能的全量验收。

- UI仅用于发现菜单、按钮、字段和功能入口，帮助定位对应业务/API；本轮不建设UI验收或自动化覆盖。
- 每个功能依次整理：来源及业务规则 → 输入/输出与状态变化 → API及源表字段映射 → 正反例、数据前置和断言。已确认规则、实现观察、待验证映射分开标注。
- 需要佐证时使用现有基础库只读样本。没有测试环境Doris不阻塞资产整理；基础库对照不证明Doris同步完整或BI全量准确。
- 首页下方图表暂不验证，历史观察保留参考；不再为图表交互或公式追问产品。
- 资产规则与缺口整理可交接后即可推进KYC，不等待BI所有用例通过、时效测完或Doris接入。新需求引用模块基线并选择相应API回归范围。
- 本约定适用于本轮后台模块整理，不改变已有P0核心UI及其他需求已授权的执行范围。

## 文件分工

- 模块README记录页面功能、指标及来源；questions记录未决问题及用户决定；test-cases记录验证清单和实际覆盖边界。
- requirements继续保存按Story组织的变更、提测和交付证据；新需求引用模块规则，明确改动及回归范围。
- 已有长期规则只引用，不复制成第二份权威规则。确认后的模块规则需标来源和日期；页面实际表现与产品预期分别记录。
- API资产继续在api/inventory、api/catalog、api/p0，执行脚本和UI元素继续在原目录；本次不迁移、不创建第二套执行框架。
- 逐页推进，先清理已确认问题，再请用户补充真正缺失的逻辑；不把当前页面或接口响应当作业务正确性证明。
