# FAT 当前接口发现与映射计划

## 背景与目标

现有接口文档主要说明“曾经定义过哪些接口”，但不能证明接口当前是否仍由客户端或管理后台使用。当前专项先以 FAT 真实 UI 为调用端事实来源，完整收集页面初始化和用户交互产生的请求，建立可追溯的接口资产；接口等级在发现、去重、映射和分类完成后再确认。

目标资产以“页面 → 控件/操作 → 请求 → 接口文档 → 状态 → 证据”为主线，能够回答：

- 当前客户端和管理后台实际调用哪些接口；
- 哪个页面、按钮、页签、筛选或列表操作触发该接口；
- 请求参数来自页面输入、当前记录、登录态、分页器还是系统默认值；
- 请求是否成功、业务状态如何、主要响应结构是什么；
- 操作产生了什么副作用，操作前后数据如何变化；
- 原接口文档是否存在、名称和分类是否正确；
- 接口是当前在用、失败、未登记、仅文档可达、已废弃、被替代还是第三方接口。

## 范围

- 环境：仅 FAT。
- 调用端：客户端、管理后台。
- UI 用途：遍历所有页面和可见状态，操作输入框、页签、筛选、分页、详情、导出及按钮，以触发真实请求；不是建设一套新的 UI 回归。
- 接口来源：UI Network、当前 FAT 前端 bundle、权限/菜单树、`api/inventory/interfaces.csv` 和 `api/catalog/`。
- 写操作：FAT 中允许执行新增、修改、删除、审核、启停、签到、领取、资金调整等操作，不按读写类型跳过。
- 等级：本阶段不修改现有 P0/P1 范围；完成真实使用面和分类后再单独评审等级。

不进入 UAT，不处理 Jenkins，不用 API 直连代替失败的 UI 操作制造通过，也不直接修改数据库业务数据。

后续另有两个独立 FAT 调用端待当前扫描完成后再建清单：合规管理后台 `https://admin-pagcor-fat.filbet2025.com/`、代理管理后台 `https://admin-agency-fat.filbet2025.com/`，以及代理前台 `https://agency-fat.filbet2025.com/`。它们当前不纳入本轮客户端/主管理后台计数；登录凭据只在用户会话中按需使用，禁止写入仓库。

## 双线程

### 线程 A：客户端

- 页面源清单：[`../client-button-map/README.md`](../client-button-map/README.md)。
- 独立结果目录：`../fat-client-interface-scan/`。
- 按 Home、Sidebar、Login、Register、My、Rewards、Free Spins、Earn Filcoins、Filcoins Mall、Game、筛选弹窗、VIP 顺序执行。
- 扫描页面初始化、登录前后状态、输入与校验、页签、筛选、列表加载、卡片、详情、主导航和所有按钮。
- 第三方游戏、支付页和客服等外部请求单独标记，不用外部页面成功代替本系统启动接口的判断。

### 线程 B：管理后台

- 页面/权限基线和结果目录：[`../fat-admin-interface-scan/`](../fat-admin-interface-scan/)。
- 使用独立 Playwright 浏览器，一次登录后持续复用会话；优先英文 UI，同时保留中文权限树和接口文档名称。
- 第一阶段只建立菜单清单：先使用菜单/权限接口获取结构，再与渲染后的左侧菜单 DOM、链接 href 和实际 pathname 核对。权限接口返回的 API `module` 不能直接当作 UI 路由。
- 完整菜单路由清单确认后，第二阶段才按菜单和页面顺序逐页访问，不随机跨页点击。
- 每页先单独记录初始化请求并建立该页控件清单，然后覆盖查询、筛选、分页、详情、导出及业务按钮。
- 不使用坐标定位，不用宽泛选择器自动点击所有页签。页签只有在明确属于当前页面控件清单时才逐个验证。
- 某页失败时记录阻塞范围，然后继续无依赖页面。

## 写操作规则

1. 写操作只作用于本轮创建或用户明确指定的测试数据。
2. 执行前保存目标 ID 和操作前状态，执行后核对响应、页面状态及必要的数据库只读结果。
3. 删除、审核、启停和资金调整无需逐次确认，但必须保存目标 ID、参数来源、前后状态和结果。
4. 某一步业务失败后先诊断和分类，不调用后续成功接口绕过该失败。
5. 数据库只用于查找记录和前后核对，不直接修改 KYC、余额、订单、流水、配置或其他业务数据。

## 查询数据策略

列表、报表、日志、订单和记录类查询优先取得有数据响应，以验证真实列表结构、详情入口和分页字段，不能只用空结果证明接口可达。

1. 时间范围按“最近 7 天 → 30 天 → 90 天 → 365 天 → 页面允许的最大范围”逐级扩大，找到代表性数据后停止扩大。
2. 每次记录开始时间、结束时间、时区、筛选字段和参数来源；时间戳单位必须以页面真实请求为准。
3. 扩大时间范围时保持合理 `page_size`，通过分页取样，不用超大单页请求拉取全部历史数据。
4. 对资金、会员、审核和日志查询，只保存脱敏后的字段名、状态和结构，不保存原始会员资料。
5. 如果最大合法范围仍为空，保留 `DOCUMENTED_REACHABLE` 或 `DOCUMENTED_UNVERIFIED`，不能据此直接判定 `STALE`。
6. 扩大查询范围后若业务失败，原样记录失败参数和范围，不改用后续成功请求覆盖失败证据。

导出动作以“当前 UI 真实点击并捕获导出接口”为接口发现完成标准。系统文件保存对话框和最终落盘属于额外客户端行为，默认不点击“保存”，也不保留包含会员或资金明细的下载文件。无数据导致导出接口返回业务失败时，仍记录该接口由当前 UI 使用，同时把本次操作按真实业务失败保留；如果只出现保存窗口或按钮点击但没有 Network/download 事件，则只能记为 `CLICKED_NO_INTERFACE_EVIDENCE`，不能宣称接口已触发。

## 每项操作的记录字段

- 调用端、一级菜单、页面名称；
- 页面 URL / 路由；
- 控件类型及按钮、页签或操作名称；
- 请求方法和标准化接口路径；
- Query/Path/Body/Header 字段及参数来源；
- HTTP 状态、业务状态和主要响应结构；
- 鉴权及角色要求；
- 实际副作用；
- 操作前后数据变化；
- 原接口文档分类、名称和来源文件；
- 是否属于当前真实使用接口；
- Network、DOM、必要截图或数据库只读核对证据；
- 异常、阻塞范围和后续依赖。

不得保存密码、Token、Cookie、OTP/TOTP、设备标识、手机号或未脱敏会员数据。常规页面不截图；截图只用于难以由 Network/DOM 表达的异常或重要写操作，并且必须脱敏。

## 分类

- `ACTIVE`：页面真实调用且成功。
- `ACTIVE_FAILED`：页面真实调用但失败。
- `UNDOCUMENTED_ACTIVE`：页面真实调用，但原接口文档不存在。
- `DOCUMENTED_REACHABLE`：文档存在且可访问，但页面扫描未发现。
- `DOCUMENTED_UNVERIFIED`：缺少合法参数、前置状态或足够证据。
- `STALE`：旧接口或当前页面已经不使用。
- `REPLACED_BY`：已被新版接口替代，并记录替代接口。
- `THIRD_PARTY`：第三方支付、游戏、客服或其他外部服务接口。
- `MISCLASSIFIED`：接口仍在使用，但原调用端或业务分类错误。

静态 bundle 或权限树中的引用只能作为候选，不能仅凭静态引用标记为 `ACTIVE`。

### 发现完成标准与历史接口处理

本专项不以“动态接口数量追平原文档数量”为完成标准。页面、子页面、详情、页签、抽屉、弹窗、行内操作、隐藏/overflow 菜单及其合法状态下可见控件全部扫描完成，并且每个可执行元素已有成功、失败或明确阻塞结论后，该调用端即可完成接口发现。

- `ACTIVE`、`ACTIVE_FAILED`、`UNDOCUMENTED_ACTIVE` 和 `MISCLASSIFIED` 必须来自真实 UI 请求证据。
- 没有被当前 UI 观察到的文档接口无需逐个直连探测，也不能仅因未观察到就全部判为 `STALE`；统一保留为文档侧静态分类资产。
- 若同一业务和资源存在清晰版本链，当前 UI 已调用 `v2`/新版路径，旧路径不再被当前 bundle、权限树或 UI 元素引用，且原文档提交/上传历史早于新版，可将旧路径标为 `REPLACED_BY` 并指向新版。
- 文件名或说明中明确包含“弃用、旧、old、deprecated、copy”等标记，且当前 UI/bundle 无引用的，可标为 `STALE_CANDIDATE`；只有替代链、历史和当前引用证据一致时才提升为 `STALE`。
- 只有路径名称包含 `v2` 并不足以证明 `v1` 已废弃；版本号、业务语义、请求字段和调用端必须能对应，避免把并存版本误判成替代关系。
- 完成后优先维护真实使用接口资产；未观察文档接口保留来源、最后可得历史、静态引用和推断理由，供后续需要时复查，不阻塞接口分级。

## 执行阶段

1. 静态盘点：建立客户端页面控件清单、后台权限树、当前 bundle 路由与接口候选。
2. 菜单发现：通过菜单接口与左侧菜单 DOM 交叉核对管理后台实际页面路径，形成有顺序的菜单路由清单。
3. 页面初始化：双线程逐页访问，先捕获每个页面自身的初始化请求。
4. 页面操作：仅按当前页面明确控件清单逐项操作并捕获请求，不做跨页面宽泛点击。
5. 数据核对：写操作保存前后状态；数据库仅作只读证据。
6. 映射分类：标准化方法和路径，与 inventory/catalog 去重比对并分类。
7. 完整性复核：查找未扫描页面、未触发按钮、缺少前置状态和无法确认的文档接口。
8. 等级评审：根据真实调用频率、业务影响、资金/权限风险和依赖关系确认等级，再决定自动化覆盖。

## 记录级写操作阶段

页面级初始化、查询、筛选和分页完成后，下一阶段转入记录级子页面与状态流。首批按 KYC、会员列表、会员详情的顺序推进；不能对列表中任意既有会员执行写操作。

1. 先创建或复用本轮专用 KYC 测试会员，保存脱敏引用、UID、初始 KYC/会员/钱包状态和创建证据。
2. KYC 线覆盖客户端资料提交、后台列表定位、详情/异动记录、通过、驳回、必要的重提，以及前台状态刷新。审核动作需要真实审批验证码；登录固定码不能代替审批码。
3. 会员线先展开列表行操作、详情路由、所有页签、抽屉、弹窗和日志子页，记录每个控件的可见条件、权限 ID、参数来源和请求；只读详情可使用脱敏既有记录建立结构证据。
4. 会员写操作只使用步骤 1 创建的 UID，并按依赖顺序执行。优先选择可核对、可恢复的修改；余额、流水清理、转代理、转线、VIP 调整、密码和风控状态等动作必须先记录原值、恢复路径及对后续动作的影响。
5. 同一状态只能按真实业务链推进。业务失败后停止该分支，不调用后续成功接口覆盖失败；不可恢复或会破坏后续状态链的动作放在该会员所有其他验证完成之后。
6. 每个子页面继续使用独立 FAT 结果文件，保存脱敏 Network/DOM、请求字段、业务响应结构、前后状态和副作用；不把手机号、证件信息、Token、Cookie、OTP/TOTP 或原始会员资料写入仓库。
7. 会员详情首页按三个业务数据源拆分核对：会员详情、KYC 详情和会员钱包；权限检查请求单独记录。“流水游戏限制”按分类 → 厂商 → 游戏的三级树扫描，展开动作与请求阶段分别取证，不能当作普通 Select。
